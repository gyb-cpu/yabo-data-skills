# 申能 DWD 流程与门禁

本文件随技能分发，是原《售电4表_迁移SOP》的可复用流程提炼；实际项目的最新规则和当期证据优先。省份、业态、表数、主体、源表、编码和数值均须按本次任务确认，不以安徽案例代替。每阶段留下 `artifacts`、`gates`（通过/阻塞/未验证及证据）、`open_questions`、`next`。

## 1 口径

当天快照 → 唯一 `BI看` → A 列省份和业态筛选；读取 A–H 和 L，I/J/K 不读取。先核对表头，以实际列含义提取业务分类、指标、单位、原粒度、计算/拆分、缺值和来源，不能照搬旧模板列号。保留文件名、日期、sheet、单元格及明确的合并范围。L 的多表逐一登记，未命名、待补充、空白和未读取分开；L 空不能作为已完成同步清单。没有当天快照时正式口径阻塞，历史资料可明确标注日期用于演练。

识别本次目标表和指标，按目标表分别去重，区分原子量、必要中间量和展示派生量，以经确认的交付契约决定是否建列。对替换逻辑记录主备源、触发条件、优先级、适用键/粒度/单位和最终空值处理。可读取区域无计算依据时登记待确认，不猜测公式。出具 Markdown 与 CSV 字段对照及待确认项；读取 `产物契约.md`。

## 2 探源和映射

对 L 列具名源逐表登记，核对 SQL 的额外依赖，分别记录来源证据、用途、源端及目标读取位置、同步方式和覆盖。经授权只读检查表和列是否存在、类型、键、数据日期范围、NULL/空串/0、更新和删除字段及索引。旧文件/注释不是现库查询。核对每种主体及交易单元别名、范围、未匹配和一对多；关联时核对省份、业态和业务键。统计实际时段数和时段维表键；目标需 96 点时，24→96 的电量守恒和电价语义必须说明。逐字段记来源、转换、证据、缺值处理、增量触发来源与待确认。

## 3 命名和平台

优先沿用已有同义字段和平台唯一词条，核对中文语义、英文名、重名、长度和类型；记录命名依据与调整。字典词根先双向查重，再按授权补录字段，核对平台建表面板未找到项；留存补录记录和平台原始 SQL。不可访问或未授权则记录候选、缺口、待执行动作，不声称平台覆盖。

**定名走五道闸，命中即停**：① 跨省已有同义列 → 直接沿用；② 平台已有唯一词条 → 照抄平台名并对齐中文名；③ 平台词根破坏成对体系（购电侧/售电侧）→ 人工覆盖为对称词根；④ 词根语义偏差但已唯一 → 接受偏差，不新增重复词根；⑤ 新造（丢词/超长/语义错）→ 加最长匹配词根或人工缩写。每个业务字段记录「中文名 / 英文名 / 类型 / 命中闸 / 简化理由」。

**命名规范**：全小写加下划线、单数名词；电量/电价/电费/加权均价用 `_energy` / `_price` / `_electricfee` / `_avgprice`；交易主体前缀成对 `purchaseside_` / `saleside_`，用户侧统一 `consumption_`；有 `timeperiod` 的表名一律 `_d96`，日表 `_d`、月表 `_m`，禁止 `_d24`。

**长度**：定名前必算，目标 ≤58 字符，PG 硬上限 63；超长须简化并记录理由。查重永远排在格式之前——字典重复词根会导致拆词静默失效，不是格式问题。英文名必须人工确认，平台自动拆词结果不得直接定名（实测会拆出无关外文词并超 100 字符），探针结果不保存。

**平台校验的是字段库登记，不是 CSV 或手写 SQL 里的英文名**；中文名未登记就一定标「未找到」。建表面板重跑后 0 个未找到才算覆盖完成，不得用「表已建出来」代替覆盖结论。导入接口可能因权限不渲染，只能逐条补录，排期按此估算。

**存量表列名优先（SOP §3.2）**：目标表已存在时，业务列名以现库既有列名为准；平台字段库只用于新增列定名。同一中文名在平台存在多条条目（一条贴近快照原文、一条是既有列名）时，**选既有列名**，并把「平台另一条目 / 最终采用 / 原因」记入补录与变更记录。改名属破坏性变更：必须单独列出影响面（下游按列名取数、血缘 `en_column`、BI 取数配置、`ALTER TABLE ... RENAME COLUMN` 计划），获授权后才执行；不得把改名混进口径变更一起交付，也不得在未被要求改名时按快照原文重定条目。

## 4 DDL

按已确认目标清单和平台产物生成 PostgreSQL 建表候选：逐字段核对名称、类型精度、注释、顺序、默认值、非空与主键；业务列后 `ext_1`–`ext_10`，`updated_time` 最末。`id` 的序列/identity/默认值与实际 INSERT 配套检查。目标有时段时使用 `_d96` 和 96 点；日、月按实际契约。已有对象先对照实际结构，明确增量变更和兼容性；无需证据不得重建表。既有对象的列名不因平台条目不同而更换，命名差异按 §3 处理。平台原 SQL、类型纠偏理由、PG DDL 分开留档。

**字段清单从 BI看 取**：按 A 列筛选后取本表 B 列数据项名，按名称去重（同一指标会因对应多个图表重复出现）。是否建列按口径决定：源表原子字段、本表内可复用的中间量建；纯展示派生量（度电费用、价差、损益、同比环比）交下游；下游 BI 直接取用的电费/合计类建。同一指标在不同表口径不同时分表建，不合并。

**类型判定**（平台类型只是候选，以业务口径与跨省一致性定稿）：

| 字段类别 | 目标 PG 类型 |
|---|---|
| `id` | `serial8` |
| `province` / `company` / `transactionunit` | `varchar(30)` / `varchar(256)` / `varchar(256)`，带 `COLLATE "pg_catalog"."default"` |
| 日期键 | `date` |
| 年月键 | `varchar(10)`，`YYYY-MM` |
| `timeperiod` | `varchar(10)` |
| 电量 / 电价 / 电费 / 收益 / 费用 / 考核 / 比率 / `ext_1..ext_10` | 一律 `numeric(20,6)` |
| `updated_time` | `timestamp(6) DEFAULT CURRENT_TIMESTAMP NOT NULL` |

硬规则：业务量值列一律 `numeric(20,6)`，不用 `float`/`double`/无精度 `numeric`；年月是唯一 `varchar(10)` 业务列，不用 `date` 或 `int`；平台类型与上表冲突时以上表为准，并写「平台原类型 → 采用类型 → 原因」纠偏清单。

**平台 SQL 是 MySQL 方言，机械转换不重新设计**：反引号→双引号；`bigint AUTO_INCREMENT`→`serial8`；`decimal(p,s)`→`numeric(p,s)`；`datetime`/`timestamp`→`timestamp(6)`；去掉 `CHARACTER SET utf8mb4` 保留 collate；列尾 `COMMENT` 与表尾 `COMMENT=` 拆成 `COMMENT ON COLUMN` / `COMMENT ON TABLE`；删 `ENGINE=`；主键显式命名 `<表>_pkey`；表名全限定 `"dwd"."<表>"`。文件头追加 `SET client_encoding = 'UTF8';` 与 `SET search_path = '';`。

主键每表有且仅有一个，inline 约束或末尾 `ALTER TABLE ADD CONSTRAINT` 全文件统一。增量按 `target_date` 删除，数据量上来会全表扫，新表建议补 `target_date` 索引。新库用 `DROP TABLE IF EXISTS` + `CREATE`；已有数据的库禁止 `DROP`，只能改名/加列，且改名必须同批修改函数 INSERT 列清单、血缘 `en_column` 和下游报表。

建表后自检：列数与方案一致；最长列名 ≤63；缺注释列 0；主键数 1；`ext_` 列 ≤10。

## 5 计算函数

按表确定签名、目标键、目标粒度、来源及驱动、关联、口径、NULL/0、日期窗口及异常处理；保留既有外部签名，生成每表一份 SQL。使用本包 `函数与验收.md`；**函数生成、改写或审查时必调 `pg-function-craft`**，留存 `scripts/check_sql_output.py --json` 实际输出作为交付证据；未安装则标明依赖缺失并阻塞该阶段，不声称使用或完成其检查。可选的是 `sqlglot`、`sqlfluff` 一类包外工具，不能拿「外部工具可选」当作跳过本包技能的借口。检查器通过不等于语法正确，仍须事务内编译验证。本技能可继续按授权进行独立取证和形成部分产物。多源场景明确独立驱动集合与增量日期来源，各源先达到目标粒度再关联；公共价格只补键。不得仅凭表名断定真实时段；合同关联须核验主体、日期及有效期。逻辑删除推导应能触发重建；物理删除不能仅靠更新时间捕获。

**时段方向（SOP §2.6）**：先数实际时段数定源粒度，不看表名。源为 24 点、目标有 `timeperiod` 时必须展开为 96 点——电量 `/4.0` 均分、电价原值沿用；不允许建 `_d24`，也不允许把 96 点源降采样成 24 点后复制回 96 槽（`_d96` 表存 96 点，96 点源按 1:1 取原值）。展开后必须验算日合计不变，差 4 倍即 `/4` 用错或漏用。同表内日粒度汇总列（如「汇总」列）在 96 点中的填充方式 SOP 未统一规定，属待确认项，不得默认复制 96 槽。详见 `函数与验收.md` §2.1、§2.2。

**时段骨架只能来自 `dim.dim_timeperiod_change`**：不得用 `generate_series(1, 96)` 拼字符串自造 96 点编码。该维表 96 行，同时给出 `time_part`（96 点）/`time_24`（24 点）/`time_48`；缺失或行数不符时阻塞。详见 §2.1 末条。

**增量口径（§2.4）**：`update_time` 增量必须收 `v_changed_dates date[]`，删除与重算都用 `= ANY(v_changed_dates)`；禁止扩成 `min/max` 区间再 `BETWEEN`。水位线用半开区间，推导与抽取过滤条件一致。逻辑删除可被捕获，物理删除不能，须在增量限制中写明。

**参数校验与返回码（§2.6）**：`p_flag` 非 0/1、`p_lookback_days` 为负、显式区间日期为空或格式不符、区间倒置，一律 `RETURN -1`；日表跨度 `> 92` 天抛 `22023` 并要求改用 `p_flag = 1` 分批。`p_flag = 0` 不得当全量；首次必须先跑 `p_flag = 1` 覆盖历史并记录上界再开增量，否则第一次增量从空水位开始，看起来「没有数据」。

**数值与空值（§2.7）**：电量/电费 `round(coalesce(x, 0), 6)`，电价只 `round(x, 6)` 不补 0；加权均价 `sum(e*p)/NULLIF(sum(e),0)`；无源列 `NULL::numeric(20,6)` 并带 `-- 无源`，不得从 `INSERT` 列清单注释掉；月表 `target_yearmonth` 只用 `YYYY-MM` 比较，`'2026-01' >= '2026-01-01'` 为假会漏删首月。

**外部契约（§2.5）**：改写既有函数须保留现有参数校验返回方式（如 `RETURN -1`）、`EXCEPTION` 包装与 `ERRCODE`、头部既有字段、观测点与临时表命名。把 `RETURN -1` 改成 `RAISE EXCEPTION` 属于破坏调用方，不得顺手改。

## 6 部署和回填

按本次明确授权执行；先查实例、对象、源和同步覆盖、目标结构与函数版本。DELETE+INSERT 重跑前：对受影响日期/主体核验维表覆盖和一对多、源记录及结果键集；备份目标区间并准备恢复；按范围试跑并核对删除/插入、键及指标差异，有异常回滚。区分事务内试跑回滚与正式提交。首次全量与日常增量分别记录实际区间、时间上界和运行结果；更新列缺失或不可信时不得称增量可靠。

## 7 验收

依据可比业务口径核对实际 DDL、签名、目标键非空和重复、主体×日期、96 点覆盖、范围及源目标对应指标；对可精确比较字段分别做双向差集，期望 0，其他差异列明原因和认可状态。核查 24→96 日量守恒、缺失/真实 0、分母为 0、逻辑删除、稀疏日期、重复执行幂等；性能结论须实际计划或负载证据。按表列数据范围、SQL、时间、结果、缺口及未验证项，空源或设计性 NULL 不伪造通过。

**技能调用留痕（对应 `函数与验收.md` 验收首项）**：先确认本次确实调用了 `pg-function-craft`，并在报告中附检查器 `--json` 的实际输出（`ok`、`violations` 数量与规则编号）及数据库编译验证结果。只有人工对照、没有任何检查器输出时，本项记为未完成，不得写「已完成静态检查」。

**三层对账（SOP §7.4）**：总量（`SUM(电量)`、`SUM(电费)`）→ 分日（`target_date`）→ 分主体/交易单元，逐级缩小。源侧 SQL 的过滤条件、别名映射、`/4` 换算必须与函数完全一致；双向 `FULL JOIN`，差额超过 `1e-6` 即列出。对账脚本必须与当前部署的函数版本同口径——函数改版后旧脚本会稳定报出与「口径变更」等价的假差异，重跑前先比对 `pg_get_functiondef` 与 `计算脚本/*.sql` 是否一致。

**三类抽样校验（SOP §7.5）**：用于跑数后快速功能校验，不能替代全量对账与幂等复跑。三个场景固定用同一张业务表、同一套日期口径、同一个 `unit_A`：① 单交易单元单日期（上月 1 日）；② 单交易单元多日期（上月 1～5 日）；③ 多交易单元多日期（上月 1～5 日，`unit_A` + `unit_B`）。预期行数 = `D × U × P × K`（日期数 × 交易单元数 × 每组合时段数 × 其他合法维度数），96 点表三场景分别为 96/480/960。必须按「日期 × 交易单元」分组核对行数，不能只比总数，否则某天缺失会被另一天重复掩盖。`unit_A` 须源表和目标表两侧上月 1～5 日均有有效数据；只目标有数、源无对应的单元不能作样本。样本不足统一标 `SAMPLE_NOT_READY` 并记录原因，不得换日期/单元/表后判定通过，替代样本只能作补充证据。

**字段缺失判定（SOP §7.6）**：缺失 = `NULL` / 空串 / 纯空白，0 不算缺失。必须区分缺行与字段空：`NO_ROWS_IN_MONTH`、`ALL_NULL` / `PARTIAL_NULL`、`HARD_NULL_BY_DESIGN`、`FIELD_NOT_EXIST`。源表没有数据的月份也要输出一行（月份 `VALUES` + `CROSS JOIN`），否则缺行会被误判成字段空。按 `fill_mode` 分类看结果，`COALESCE_0` 的 0 必须回源表核对 `zero_rows`。

**验收签收单（SOP §7.8）**：行数/日期范围/主体数已记录；缺口日 0 或已解释；每主体每日行数与粒度一致；源表三层差额 0；业务键重复 0；连跑两次一致；字段缺失已按 `fill_mode` 解释；已知 NULL 列已登记原因与责任人。

## 8 血缘

核实 `dim.dim_dictionary_blood`、`dim.dim_dictionary_blood2` 的各自结构、已存在有效记录与本批业务键；依实际结构分别生成登记内容，不手写依赖序列的 ID。以项目 SOP 的基础列候选 `id、province、company、transactionunit、target_date、target_yearmonth、timeperiod、updated_time` 和 `ext_` 数字扩展列作为排除起点，结合本次实际表定义确认其确属技术/维度列；不在名单中的其他基础列及名称相同但承担业务指标的列须逐项确认，不能仅凭列名遗漏业务字段。以确认后的业务列登记表名、原始中文注释、来源及口径。登记维度为省份、业态、业务类型（候选字段 `province、marketparticipant_type、business_type`），字段级查重和配对至少核对表名及字段名；在现库核实字段与作用域后确定唯一键。若有 `is_deleted`，核实有效值；若有批次字段则采用已确认批次，否则留存本次精确键集及变更记录，不假设时间戳就是批次。缺少必要注释、身份或唯一范围时阻塞写入。授权后成对写入，逐表校验列存在、注释、遗漏、重复，两表按业务键和批次成对，差异检查应为 0；核对实际状态分布与批次数量，记录精确回滚范围。未写入应标待执行。

**登记规则**：`cn_table_name` 取 `COMMENT ON TABLE` 原文，`cn_column` 取 `COMMENT ON COLUMN` 原文，不美化、不删科目编码（源注释带 `0101中长期交易结算电费` 就原样登记）；`remark` 写计算规则，无规则写 `NULL` 不写空串；`is_deleted = 0`；`id` 交给序列。`business_type` 不带 `-96`/`-天`/`-月` 后缀（历史已因此撞车）。`blood` 与 `blood2` 的 id 空间独立，跨表不可复用。先审核待写入行，再按各表真实结构分别 `INSERT`，不套用他省历史列数。

**登记后逐表校验，除 `is_deleted` 分布外全部要求 0 行**：① 字典字段在 DWD 表里存在；② `cn_table_name` 等于表注释；③ `cn_column` 等于列注释；④ DWD 有业务列但该表未登记；⑤ 同表同字段重复有效记录；⑥ 两表按业务键成对（业务要求各一份时按成对核对，不误报为重复）；⑦ `is_deleted` 分布；⑧ 本批新增行数等于变更单数量。

**回滚**：用批次或精确键集把 `is_deleted` 置 1 并刷新 `updated_time`，两张表各执行一次；回滚谓词不得照搬他省历史日期。

## 9 交接

按实际产物更新省份根目录及计算脚本 README：快照、目标对象、字段及函数版本、本地与现库差异、运行/验收范围、变更、遗留和证据。分别标候选、事务回滚、部署、回算、验收，不拿旧报告冒充当前。根目录、DDL、参考资料、计算脚本和复核验证按 `产物契约.md` 组织。

**五维审查（SOP §9.1）**：语义（筛选条件、聚合口径、`/4`、join 键、空值语义，`static-risk`）；性能（重复扫描、全表聚合、函数内循环、缺索引、隐式转换，`plan-required`）；幂等（删除范围 = 插入范围、业务键唯一、重跑漂移，`static-risk` 加运行验证）；边界（空参、空串、非法日期、倒置区间、跨月跨年、结束日，`static-risk`）；风格（`LANGUAGE`、缩进、临时表命名、分号位置，可复核）。

**等价性验证（SOP §9.2）**：归一化比对只能证明文本等价，不能证明结果一致；结果级验证要先备份目标区间、跑新函数、再做双向 `EXCEPT`，两向都必须 0 行；并核对业务键唯一、连跑两次行数一致、`pg_proc` 中签名与返回类型不变。性能须 `EXPLAIN (ANALYZE, BUFFERS)`，未实测不写「已优化」。

**变更分离（SOP §9.3）**：语义修复与格式重排必须是两个 diff；整文件重排会让 diff 变成无法评审的单个 hunk。不要顺手加回看窗上界、按月分片、`ON COMMIT DROP` 或改参数类型，这些都属于行为变更。

**交付前 P0 清单（SOP §9.4）**：测试库 `CREATE OR REPLACE` 成功且签名/返回类型不变；归一化差异逐条写明等价理由；`INSERT` 列数等于外层 `SELECT` 项数；列清单与表列集合差集恰为 `{id, ext_1..ext_10, updated_time}`；结果双向差集 0/0；业务键重复 0 行且连跑两次行数相同；diff 只含预期 hunk；无残留调试 `EXECUTE` 与哨兵日期。

**交付物（SOP §9.5）**：建表语句、计算脚本（每表一个函数文件）、待建字段清单与字段映射表、平台补录与变更记录、执行与验收 SQL、验收报告、血缘登记 SQL 与校验结果、评审报告。已回退的近似列必须在变更记录和待确认清单留痕，并在交付物中单列「已回退列」，避免下游误以为有数。
