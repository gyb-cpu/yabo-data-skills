# 首次开发（bootstrap 模式）

本文件只约束 `bootstrap` 模式。首次开发的目的只有一个：交付经过建表工匠字段补录的正确 DDL，以及引用了全部源表的计算函数初稿，让用户在目标环境建表，并让平台从函数 SQL 自动解析血缘、把源表同步到目标库。函数口径允许不完全正确，准确性、对账、写库、血缘登记和评审都留给源表同步后的 `full` 模式。

## 1 模式判定

| 模式 | 判定 | 本次范围 |
|---|---|---|
| `bootstrap` | 提示词写明首次开发；或目标库中查不到本次 `BI看` L 列具名的源表 | 本文件 §3 的 5 个步骤，交付 §4 的固定产物后停止 |
| `full` | 提示词写明源表已同步；或源表在目标库读取位置均已存在且有数据 | [流程与门禁](流程与门禁.md) 阶段 1–9 |
| `maintenance` | 目标表已在目标库存在且有数据 | 按存量维护流程，列名以现库为准 |

提示词与库内实况冲突时（例如写明首次，但目标表已存在且有数据），停止并报告冲突，不自行切换模式。`bootstrap` 模式即使获得更大授权，也不顺延进入 `full` 的阶段。

## 2 读取与工作区边界

- 只读：本 `SKILL.md`、本文件、用户给出的 BI 看快照与参考业务逻辑文件、项目根目录的 `.env.shenergy`。写函数时只按需查阅 [函数与验收](函数与验收.md) §2.1、§2.3、§2.4、§2.6、§2.7、§2.8；命名与 DDL 规则只查 [流程与门禁](流程与门禁.md) §3、§4。其他 references 在本模式不读。
- 快照只读 `BI看` sheet，用 `scripts/parse_bi_snapshot.py`（默认 `--sheet BI看`）解析；工作簿中的其他 sheet 不打开、不解析、不引用。
- 只在 `<省份><业态>/` 目录下创建文件。项目根目录不是空目录时，不扫描、不读取、不修改该目录以外的文件，除非用户在提示词中点名。
- `<省份><业态>/` 已存在时先停下，报告其中已有的文件并询问是覆盖、另建目录还是改用 `maintenance`，不合并、不覆盖。
- 不安装依赖、不创建虚拟环境、不写临时测试脚本或探针脚本、不执行 git 操作、不修改技能目录、不重复运行 `verify_offline.py`。

## 3 步骤

1. **口径（阶段 1 精简）**：`python scripts/parse_bi_snapshot.py <snapshot.xlsx> --sheet BI看 --province <省> --business <业态> --out-csv <省份业态>/参考资料/指标字段来源对照表.csv --json`。按目标表去重 B 列指标，结合参考业务逻辑文件确定建列范围；L 列逐表登记源表名。用 `scripts/check_shenergy_artifacts.py --kind csv --json` 校验 CSV。口径不清的指标记入待确认清单后继续，不反复追问。
2. **源端探查（阶段 2 精简）**：只读源 MySQL，对 L 列每张具名源表确认存在、列名与类型、时段数（判 24/96 点）、`update_time` 与 `deleted` 字段是否存在。目标 PostgreSQL 只查三件事：目标表是否已存在、`dim.dim_timeperiod_change` 是否存在、源表在目标端读取位置是否存在（用于模式判定）。不做空值分布、一对多、覆盖范围和数据量统计，这些属于 `full` 模式。
3. **命名与平台补录（阶段 3，必做）**：按五道闸定名，在建表工匠做字典查重与字段补录，重跑建表面板直到 0 个「未找到」，导出平台原始 DDL 原样留档。平台补录是平台写操作，提示词未授权或平台不可用时停在候选名，DDL 标「候选未定稿」，不宣称覆盖完成。
4. **DDL 与 Spec（阶段 4）**：按 [流程与门禁](流程与门禁.md) §4 把平台 MySQL 方言机械转换为 PostgreSQL DDL，产出每表 `<目标表名>_spec.json`，运行 `--kind spec` 与 `--kind ddl --spec` 检查。
5. **函数初稿（阶段 5 精简）**：调用 `pg-function-craft` 的 `generate` 模式，传入 Spec 与 [函数与验收](函数与验收.md) §2.10 Profile，并声明本次为首次草稿：只加载其 `04-固定风格.md`，排版违规时再查 `06-SQL排版规范.md`，不做 `07`/`08` 的性能与审查流程。硬约束照常执行（96 点骨架取 `dim.dim_timeperiod_change`、增量用 `date[]`、参数校验、函数头位置、不写 `ext_1..10`）。运行 `scripts/check_shenergy_artifacts.py --kind func --with-pg-checker --spec <spec.json> --json <func.sql>`，每个文件最多修 2 轮，仍未通过则把剩余违规原样写入 README 的 `gates`。

**血缘相关硬要求**：平台从函数 SQL 自动解析血缘，因此函数中每个源表必须写成目标端读取位置的全限定名（`<schema>.<表>`），覆盖 L 列全部具名源表及参考逻辑中的额外依赖；不得用动态 SQL 拼接表名，不得把源表放进注释代替实际引用。目标端 schema 无法确定时写候选名并记入待确认清单。

本模式不做：数据库编译验证、部署、回填、对账与抽样、字段缺失判定、血缘表登记、五维评审、评审报告与验收报告、执行与验收 SQL、源表登记与同步清单（平台自动解析）。

## 4 固定产物

`bootstrap` 结束时 `<省份><业态>/` 下只应有以下文件（`N` 为目标表数，每表一份 Spec 和一份函数）：

```text
<省份业态>/
├─ README.md                                   # mode、各产物状态、artifacts/gates/open_questions/next
├─ 参考资料/
│  ├─ <任务当天快照>.xlsx                      # 可选：快照副本
│  └─ 指标字段来源对照表.csv
├─ DDL/<省份><业态><N>表_建表语句.sql
├─ 计算脚本/<目标表名>.sql
└─ 复核验证/
   ├─ <省份业态>_平台补录与变更记录.md         # 定名、命中闸、查重、0 未找到证据
   ├─ <省份业态>_平台原始DDL.sql
   ├─ <目标表名>_spec.json
   └─ <省份业态>_待人工确认清单.md
```

交付前运行 `python scripts/check_shenergy_artifacts.py --kind bootstrap --json <省份业态目录>`，确认文件齐全、没有多余产物、Spec 与函数一一对应、README 含模式与四个汇报键。

## 5 停止与汇报

上述检查跑完即结束本次任务，不继续优化口径或性能。最终回复固定为四段，每段只列事实：

- `artifacts`：产物路径及状态（定稿 / 候选 / 草稿）。
- `gates`：CSV、Spec、DDL、函数、bootstrap 检查器的 `ok` 与违规数；平台「未找到」数量。
- `open_questions`：问题、影响字段、需要谁确认。
- `next`：① 在目标库执行 DDL（需单独授权）；② 在平台按函数血缘同步源表；③ 同步完成后发送 `full` 模式提示词。
