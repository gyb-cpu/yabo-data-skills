# 函数开发与验收

## 开发前

逐表确认目标表结构、业务唯一键及粒度、既有函数签名和调用契约；列出每个指标的源、转换、过滤、单位、缺值规则及依据。核查源表实际字段、日期、更新和删除方式、关联键、主体维表覆盖及重复，记录不可验证项。结构或关键口径缺失时只交付已确认部分和缺口，不编造可部署函数。

## 函数设计

1. 按目标业务键建立各个独立源的驱动键全集，避免以某一个稀疏源作为唯一驱动而丢失其他来源；公共价格等补充源按已确认键补值，避免无业务依据的主体扩张。
2. 每个源先按目标粒度聚合或去重再关联；核对连接键和有效期，防止一对多放大。时段维表按项目实际定义转换，明确起止与边界；需要 96 点时检查每个主体日期的时段完整性。加权分母无依据时停止相关计算。

### 2.1 时段换算方向（SOP §2.6 明文，不得自行选择）

先数实际时段数判定源粒度，不看表名：`count(DISTINCT time_part)` 在该表有数日期上约为 24 即 24 点源，约为 96 即 96 点源。

| 源 → 目标 | 电量 | 电价 |
|---|---|---|
| 24 → 96 | `energy / 4.0`（均分到 4 个槽） | 原值沿用，同一小时 4 个槽取相同值 |
| 96 → 96 | 原值；源为功率（MW）则 `/4` | 原值 |
| 96 → 24 | **不允许**：目标表只要有 `timeperiod` 列就只能存 96 点 | — |
| 24 → 24 | **不允许**：不得建 `_d24` 表 | — |

- 展开写法：主体清单 `CROSS JOIN dim.dim_timeperiod_change`，按 `源.time_part = t.time_24` 关联，输出 `t.time_part`。先确认该维表 `time_part` 是 96 点槽、`time_24` 是 24 点槽，不同省脚本的关联方向有反例。
- **禁止自造时段骨架**：不得用 `generate_series(1, 96)` 拼 `lpad(...) || ':' || lpad(...)` 之类方式构造 96 点时段。`dim.dim_timeperiod_change` 是唯一的时段来源，它同时承载 `time_part`（96 点）、`time_24`（24 点）、`time_48`（48 点）三套编码；自造骨架会造成同一项目内时段口径分叉，且绕过了对该维表的覆盖校验。该维表缺失或行数不为 96 时阻塞，不得用生成序列兜底。
- 展开后必须验算日合计不变：目标 96 点日合计 = 源 24 点日合计。这是验收必查项，差 4 倍说明 `/4` 用错或漏用。
- `/4` 必须写注释区分语义：「24 点均分」与「MW×0.25h 功率转电量」数值相同但含义不同。
- 本技能适用范围不含把 96 点源降采样成 24 点后再复制回 96 槽的写法。目标表是 `_d96` 且源也是 96 点时，按 1:1 取该时点原值。

### 2.2 日粒度指标在 96 点表中的存放

同一指标若同时存在分时列与汇总列（如「中长期合约电量（分时）」与「中长期合约电量（汇总）」），汇总列的时段填充方式必须在表级口径卡中明确写明，不得默认把日值复制到全部 96 槽——复制会让该列 `SUM` 放大 96 倍。SOP 未对此给出统一规定，属需业务确认项；确认前按「只写一个时段或由业务指定」，并在待确认清单登记。
3. 将真实零值、源缺失、NULL、删除分别处理；分母为零时依确认口径处理，不能凭空赋零。替换逻辑标明优先级、适用条件与缺失判定。
4. 增量应纳入所有能影响结果的源及逻辑删除变化，保留实际变化日期或月份集合；删除与重算使用同一集合，禁止将稀疏集合简单扩为 min/max 区间。显式业务区间重跑单独处理。物理删除、维表变化及缺失/不可靠更新时间需要可验证的补偿机制，否则标记增量限制。
5. INSERT 显式列清单与 SELECT 逐项对齐，确认 id 的默认值或序列；保留既有函数签名及必要异常处理，DDL 与函数字段顺序和类型一致。检查重复扫描、无必要关联及索引适配，但性能结论依赖实际执行证据。

### 2.3 返回类型与返回契约（必须能装下行数）

SOP §5 模板写的是 `RETURNS smallint`，**这是模板缺陷，不要照抄**。`smallint` 上限 32767：

- 96 点表单个主体日的行数是 96，6 个主体 3 个月就是 21312 行；季度级或年度级重跑必然溢出。
- 溢出时报 `NumericValueOutOfRange: smallint out of range`，且**发生在函数末尾 RETURN 处**——前面 `DELETE` 与 `INSERT` 已经执行，看起来像"跑成功了但数据没变"，极易误判。
- 新建 DWD 函数一律使用 `RETURNS integer`（上限 21 亿），声明 `v_rows integer := 0;`（或通过 `GET DIAGNOSTICS v_rows = ROW_COUNT;` 累计插入行数），成功时 `RETURN v_rows;`（返回 `>= 0` 影响行数，`0 行也算正常`），参数非法时 `RETURN -1;`。分区重跑时更要注意：单段行数超 32767 就失败。
- 既有线上函数若原本返回状态码 `0`（不返回影响行数），按 §2.5 保留其既有签名与返回语义，不擅自破坏调用方契约。

### 2.4 增量必须按变化集合，不得退化为 min/max 区间

按 `update_time` 做增量时，删除与重算都只针对本次**实际变化的业务日期集合**：

- 从变更行反推日期用 `array_agg(DISTINCT <业务日期>) FILTER (WHERE ... IS NOT NULL)` 收进 `date[]` 变量（月表收 `v_changed_months`），删除与插入都用 `= ANY(v_changed_dates)`。
- **推导 `v_changed_dates` / `v_changed_months` 的查询禁止过滤 `deleted = 0` / `is_deleted = 0`**（具体机制与静检由 `pg-function-craft` `11-增量与水位线.md` `INC-07` 与 `check_sql_output.py` 统一承担）：逻辑删除会把 `deleted` 置为 `1` 并刷新 `update_time`，若在推导阶段过滤会导致目标表残留脏数据；`AND a.deleted = 0` 仅写在后续 `INSERT ... SELECT` 抽取查询中，推导与抽取保持一致的 `update_time` 窗口。
- 水位线用半开区间 `[clock_timestamp() - p_lookback_days, clock_timestamp())`，避免把本批执行期间新提交的行卷进来。
- **禁止把稀疏变化集合扩成 `min/max` 区间**再 `BETWEEN` 删除。源端只回补了 3 天时，扩区间会重算并删除整段，既放大锁与写入量，也把未变化的日期一并覆盖；这属于把「按水位线增量」退化成「按区间全量重算」。
- 逻辑删除会刷新 `update_time`，能被回看窗捕获；物理删除不会，必须在增量限制中写明。

**与 SOP §5.3 模板的关系**：SOP 的 `min(d.biz_date)` / `max(d.biz_date)` 反推区间写法（对应 `pg-function-craft` 的 `INC-04`）只保证「不漏」，不保证「不重写」——源端只回补 3 天时它会把整段一起删重建。两种写法按场景选，并在表级口径卡写明用了哪种：

| 场景 | 写法 |
|---|---|
| 日常稀疏增量（回补几天） | `v_changed_dates date[]` + `= ANY(...)`，**默认选它** |
| 首次全量或确认需要整段重算的显式区间 | `p_flag = 1` 显式区间，等价于 `min/max` 连续覆盖 |

既有多数线上函数已用 `v_changed_dates date[]`（见本文件 §2.5 的外部契约要求），改造时不要为了贴合 SOP 模板而改回区间写法。

### 2.5 保留既有函数的外部契约

对照目标库现有同名函数，改写时保留下列契约，改变即视为破坏调用方：

- 参数校验失败时的返回方式（如 `RETURN -1`）与既有成功返回值语义（例如既有函数原本返回状态码 `0` 时保留 `0`）；不要改成 `RAISE EXCEPTION`。
- `EXCEPTION WHEN OTHERS` 包装及其 `USING ERRCODE = SQLSTATE`；调用方依赖错误码。
- 函数体内 `*increment` 等既有字段；八字段是下限，既有字段只增不减，头部必须可由 `pg_get_functiondef` 导出。
- 生产路径的 `RAISE DEBUG`/`RAISE WARNING` 观测点。
- 临时表的业务前缀命名与显式 `DROP`，两处必须成对。

新增例外需逐条登记理由，不静悄悄替换。

### 2.6 参数校验与返回码（SOP §5.2、§9.1）

进门先校验，不满足一律 `RETURN -1`，不得静默跑全量或静默改窗口：

| 检查 | 条件 |
|---|---|
| `p_flag` | `IS NULL` 或不在 `(0, 1)` |
| `p_lookback_days` | `IS NULL` 或 `< 0` |
| 显式区间日期 | `p_flag = 1` 时 `p_start_date` / `p_end_date` 为 `NULL`，或不匹配 `^\d{4}-\d{2}-\d{2}$` |
| 区间倒置 | `v_start_date > v_end_date` |
| 跨度保护 | 日表跨度 `> 92` 天时 `RAISE EXCEPTION ... USING ERRCODE = '22023'`，提示改用 `p_flag = 1` 分批 |

- `p_flag = 1` 按显式区间重算；`p_flag = 0` 按 `update_time` 增量，日期参数不生效，可传空串。**不得把 `p_flag = 0` 当全量**。
- 返回契约（与 §2.3、§2.8 统一）：新建 DWD 函数正常返回 `v_rows integer`（`>= 0` 影响行数，0 行也算正常），`-1` 参数非法；既有函数若原契约返回状态码 `0`，按 §2.5 保留 `0`（0 行也算正常）与 `-1` 参数非法。头部 `*output` 承诺的分支必须在代码里能到达。
- 月表按实际契约传 `YYYY-MM`；内部仍做 `::date` 的例外函数（如 `_clearing_m`）要单独说明。
- `EXCEPTION` 遵循 `pg-function-craft` `REV-C01` / `AP-02`（只做兜底重抛并保留原 `SQLSTATE`；禁止 `WHEN OTHERS THEN NULL`，禁止改写成「返回 0 表示成功」，也不要用它包正常分支）。

### 2.7 数值、空值与无源列（SOP §5.5、§5.6）

- 电量/电费：`round(coalesce(x, 0), 6)`；电价只 `round(x, 6)`，**不补 0**（无量即无价）。
- 加权均价：`sum(energy * price) / NULLIF(sum(energy), 0)`，不写 `avg(price)`；分母为 0 返回 `NULL` 而非 0。
- 比率：分母为 0 返回 `NULL`。源表缺数与真实 0 必须分开记录，`COALESCE_0` 的 0 要回源表核对。
- 无源列：`NULL::numeric(20,6) AS <列> -- 无源：fill_mode=HARD_NULL`。不以别的列近似，近似必须业务书面确认并登记。
- 不得把无源列从 `INSERT` 列清单里注释掉；`INSERT` 列清单与外层 `SELECT` 项必须逐行等长。
- 月表 `target_yearmonth` 只用 `YYYY-MM` 定长零填充比较：`'2026-01' >= '2026-01-01'` 为假，会漏删首月。

### 2.8 函数头位置与导出可见性

函数头必须写在函数体内部：位于 `AS $function$` 之后、`DECLARE` 或 `BEGIN` 之前。不能只写在 `CREATE OR REPLACE FUNCTION` 之前，因为 PostgreSQL 的 `pg_get_functiondef` 不保留 `CREATE` 前的普通 SQL 注释；只有函数体内的注释才保存在 `prosrc`，并在部署后随函数定义导出。

固定格式：

```sql
CREATE OR REPLACE FUNCTION dwd.f_<domain>_<action>(
    p_flag integer
    , p_start_date character varying
    , p_end_date character varying
    , p_lookback_days integer
)
RETURNS integer
LANGUAGE plpgsql
SECURITY INVOKER
SET search_path = ''
AS $function$
/*****************************************************************
*name       : dwd.f_<domain>_<action>
*function   : <业务语义>
*input      : p_flag 0=增量 1=按日期区间, p_start_date, p_end_date, p_lookback_days=回看天数
*output     : -1参数异常, >=0影响行数
*increment  : update_time 水位线，半开区间 [clock_timestamp()-p_lookback_days, clock_timestamp())
*author     : <原作者；新增函数写 待补充；不得伪造署名>
*CreateDate : <YYYY-MM-DD>
*UpdateDate : <YYYY-MM-DD>
******************************************************************/

DECLARE
    v_rows integer := 0;
BEGIN
    ...
    RETURN v_rows;
END;
$function$;
```

通用头部排版、日期追加与分隔线机械规范统一遵循 `pg-function-craft`（`F-21`、`F-36`–`F-41`），申能项目特定契约如下：

- `*name` 使用 schema 全限定名并与 `CREATE FUNCTION` 一致；`*input` 写明全部 `p_` 参数业务含义。
- `*output` 必须与实际返回一致：新建 DWD 函数一律返回 `v_rows integer` 影响行数，固定写 `-1参数异常, >=0影响行数`；仅既有函数按 §2.5 保留原状态码 `0` 时写 `-1参数异常, 0正常`。
- `*increment` 必填：增量函数写水位线、回看窗口与半开区间，非增量函数写 `不适用`。
- `*author` 改写时保留原作者，新增函数写 `待补充` 或用户明确提供的作者。

### 2.9 扩展字段不进入计算脚本

`ext_1`–`ext_10` 是目标表的平台/DDL 预留扩展列，不属于计算脚本的业务口径。计算函数不得将 `ext_1`–`ext_10` 写入 `INSERT` 列清单，也不在 `SELECT` 投影中生成对应值或 `NULL` 占位；字段映射、来源登记和单位核对同样不把它们当作业务指标。目标表结构验收时只检查这些列存在，不为了“列数对齐”造值；静态门禁由本技能 `scripts/check_shenergy_artifacts.py` 的 `SH-FN-04`（仅检查 `INSERT`/`SELECT` 投影，豁免 `WHERE`）单独承担。

### 2.10 与 `pg-function-craft` 的优先级与覆盖声明

按照 `pg-function-craft/references/00-风格与边界.md` §6「冲突优先级」，本技能（`shenergy-dwd-development`）的规范属于第 2 层「项目已确认的书面约定」，且两个技能已统一以 **原生 PostgreSQL 12+（`pg12+`）** 为默认数据库基线。进入阶段 5 调用 `pg-function-craft` 时，除递交脱敏的 `<目标表名>_spec.json`（见 `产物契约.md`「表级函数规格卡」）外，固定附带以下调用上下文（Profile）：

```yaml
target_engine: pg12+                # 默认原生 PG 12+；可按实际目标库声明 pg14 / pg16
return_contract: row_count          # 新建 DWD 函数为 row_count；既有status 0函数按 §2.5 传 status_code
comma_style: leading
project_overrides: [ENG-11, ENG-26]
```

边界裁决如下：

1. **不可覆盖的第 1 层（安全与正确性底线）**：`pg-function-craft/references/01-基线规范.md` 与 `pg-function-craft/references/02-反模式.md` 中的规则（默认 `SECURITY INVOKER`、`SECURITY DEFINER` 固定最小 `search_path`、动态 SQL 用 `format('%I')` 与 `USING`、禁止 `WHEN OTHERS THEN NULL`、禁止 `v_changed_dates` 推导过滤逻辑删除 `INC-07` 等）为最高优先级，申能项目约定不得降低这一层。
2. **第 2 层对通用工程默认值的明确覆盖（仅限申能 DWD 项目）**：
   - **参数校验与超限跨度保护**：本文件 §2.6 规定的日期格式正则 `^\d{4}-\d{2}-\d{2}$` 校验与日表跨度 `> 92` 天时 `RAISE EXCEPTION ... USING ERRCODE = '22023'`，覆盖 `pg-function-craft/references/09-工程与函数结构规范.md` 中的 `ENG-11`（允许常规参数异常 `RETURN -1` 与超限跨度保护抛 `22023` 并存）和 `ENG-26`（保留项目要求的格式正则与 92 天保护）。
   - **返回影响行数契约**：本文件 §2.3 与 §2.8 规定的新建函数 `RETURNS integer` + 返回 `v_rows integer`（`*output : -1参数异常, >=0影响行数`），覆盖通用模板默认值 `0正常`；既有函数保留 `0` 状态码时按 §2.5 处理。
   - **扩展字段排除单一归属**：`ext_1`–`ext_10` 不进入计算脚本的 `INSERT`/`SELECT` 属于申能 DWD 表契约，由本技能 `SH-FN-04` 单独检查；`pg-function-craft` 不重复检查该项目规则。
3. **其余通用默认值**：未被本技能覆盖的排版 `MUST`（第 3 层）与函数工程默认值（第 4 层）均按 `pg-function-craft` 原生 PG 12+ 基线执行（不套用 GP 6.6 / PG 9.4 降级约束）。

## 静态检查

逐表检查语法结构、对象与列名、字段映射、列数和类型、目标键、驱动覆盖、聚合后连接、日期集合、边界条件、删除与插入范围一致、NULL/0 及异常处理。

**`pg-function-craft` 与随包检查器都是必调项，不是可选工具。** 写函数前先调用 `pg-function-craft`（传入 `<目标表名>_spec.json` 与 §2.10 Profile），交付前在技能根目录运行一键双检门禁并留存实际 JSON 输出（安装到项目后按实际安装路径执行，禁止写死仓库前缀）：

```bash
python scripts/check_shenergy_artifacts.py --kind func --with-pg-checker --spec <spec.json> --json <计算脚本.sql>
```

该命令同时执行 `check_shenergy_artifacts.py`（申能 DWD 业务契约 `SH-FN-01`–`08`、`SH-FN-10`–`11`，含唯一归属的 `SH-FN-04` 与 `--spec` 列清单/顺序及驱动源检查）与同级 `pg-function-craft` 的 `scripts/check_sql_output.py --json`（通用 PG 12+ 排版与安全/正确性，含唯一归属的 `INC-07`），合并输出无重叠双层检查结果；如需独立运行，亦可分别执行 `scripts/check_sql_output.py --json` 与 `scripts/check_shenergy_artifacts.py --kind func --json`。月表未传 `--spec` 时加 `--grain month`，既有函数改造未传 `--spec` 时按实际契约加 `--legacy`。

区分两类工具：

| 类别 | 举例 | 要求 |
|---|---|---|
| 本包配套技能 | `pg-function-craft` 的规则与检查器、`shenergy-dwd-development` 的 `scripts/check_shenergy_artifacts.py` | **必调**；未安装则阻塞函数生成/改写/审查，不得声称已使用 |
| 包外第三方工具 | `sqlglot`、`sqlfluff`、`pg_format` | 可选；用了要记录版本与输出，没装要说明 |

`pg-function-craft` 与 `check_shenergy_artifacts.py` 的 `ok: true` 只代表文本/契约规则通过，**不代表语法正确**（它们不做 PostgreSQL SQL 解析）。两项通过后仍必须做数据库编译验证：可用 `scripts/generate_validation_sql.py --kind compile --spec <spec.json>` 生成事务包装脚本，在事务内建临时对象执行 `CREATE`，验证 `pg_get_functiondef` 后再 `ROLLBACK`，不落库。静检与编译验证两步都完成了才能写「静态检查通过」。

静态检查不能证明 SQL 能在目标数据库运行或满足性能要求。

## 授权执行与验收

执行前确认目标环境和对象，核实源同步、目标 DDL、函数版本、主体映射以及日期与主体覆盖。DELETE+INSERT 前备份受影响目标区间并准备恢复；确认受影响源和重建键集覆盖预期范围，存在缺口或异常则停止。备份与变更的事务策略按实际数据库与权限确认；记录备份标识和恢复步骤。

验证 SQL 模板优先用 `scripts/generate_validation_sql.py --spec <spec.json>` 生成（支持 `--kind compile|reconcile|sample|missing|blood|all`），再按实际授权、真实源表与业务口径替换占位符执行。

按实际授权区分事务试跑回滚、部署、正式回算。逐表检查：

- **技能调用留痕**：确认本次函数生成、改写或审查确实调用了 `pg-function-craft` 与申能专属检查器，并在报告中附 `scripts/check_shenergy_artifacts.py --kind func --with-pg-checker --json` 的合并输出，或同时附 `scripts/check_sql_output.py --json` 与 `scripts/check_shenergy_artifacts.py --kind func --json` 的实际输出（均含 `ok`、`violations` / `violation_count`、规则编号）。只有人工对照检查、没有任何检查器输出时，本项视为未完成，报告中不得写「已完成静态检查」。同时记录数据库编译验证（`ROLLBACK`）的结果。
- 结构与注释符合定稿；业务键非空、重复数为 0，日期和主体覆盖符合明确预期。
- 针对要求 96 点的表，每个应有主体×日期恰有 96 个不同且合法的时段；缺口、额外时段和重复分别为 0，例外须业务确认。
- 在相同过滤、粒度、单位和缺值口径下，源目标键及可精确比较的指标双向差集为 0（使用 `generate_validation_sql.py --kind reconcile` 生成三层对账模板）；浮点或舍入场景按经确认的容差记录差异，不以空源充当通过。
- 验证真实 0、无来源、分母为 0、逻辑删除、稀疏变化日和显式区间；相同输入重复运行结果一致。24→96 按确认的电量单位核对汇总守恒；三类抽样与字段缺失五态分别使用 `--kind sample` 与 `--kind missing` 模板核对。
- 记录 SQL、环境、执行时间、范围、数量、差异、容差及异常；函数返回值不代表数据正确。性能须有实际执行计划或负载证据。

血缘按 `dim.dim_dictionary_blood` 与 `dim.dim_dictionary_blood2` 两张表实际结构、批次和业务键独立登记与校验（可用 `generate_validation_sql.py --kind blood` 生成 8 项核对与按批次/键集回滚脚本），分别检查字段、注释、遗漏、重复以及两表配对；差异预期为 0，例外注明原因与确认状态。只执行授权范围内的写操作。
