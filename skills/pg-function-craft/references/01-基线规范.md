# PostgreSQL 工程基线

这些是默认要求，不针对任何个人风格或语料。项目已确认的版式偏好可以覆盖书写形态，
但安全与正确性约束不能被“既有代码里就这样写”推翻；确需偏离时必须附风险说明。

既有代码与基线的冲突不等于默认值错了。冲突时按本文件与 `references/02-反模式.md` 处理。

## 安全

- 默认 `SECURITY INVOKER`。
- 必须用 `SECURITY DEFINER` 时，必须固定最小可信 `search_path`，两种写法**二选一**，不得混用：
  - `SET search_path = pg_catalog, <受信 schema>, pg_temp`，`pg_temp` **显式放在最后**；
  - `SET search_path = ''`，并要求函数内所有对象全限定。

  不要只写"排除 `pg_temp`"——未显式列出时，`pg_temp` 对表/类型名默认先于 `search_path` 中的
  schema 被搜索，只有显式定位才能把它压到受信 schema 之后。同时尽量限定对象名，并复核
  `PUBLIC` 执行权限与属主权限。
- 动态 SQL 必须把标识符（`format('%I', ...)`）与值（`EXECUTE ... USING`）分开。不得拼接不可信值。
- 不得静默改变 RLS 或权限行为。
- 从 `pg_get_functiondef` 导出的文本不含 `GRANT`/`REVOKE`、`COMMENT`、属主与 ACL。
  "文本里没有授权语句"不能证明原函数未授权，也不能据此复刻权限配置；权限要看
  `pg_proc.proacl`、`pg_class.relacl` 或实际授权记录。

## 正确性

- 不要用 `WHEN OTHERS` 把错误变成 NULL、空结果、提示或假成功。只在恢复动作明确时捕获；
  需要时用 `RAISE` 重抛。
- volatility 与 strictness 按实际行为声明。读表或依赖时间的函数不得标 `IMMUTABLE`。
  只读函数保持默认 `VOLATILE` 也是正确的；`STABLE` 是优化器提示，只在函数不写库、且同一条
  语句内结果稳定时才标。不要仅因"它是只读的"就强制改成 `STABLE`，也不要为此改变既有接口。
- NULL 行为、空结果行为、幂等性、影响行数语义必须写明。0 行可以是合法结果（空日期区间、
  源表无增量），不得把 `ROW_COUNT > 0` 当作成功条件。
- 函数无法控制事务；存储过程（`CALL`）可以提交/回滚，事务语义与函数不同，需要单独解释边界。

## 落表路径验证

以下约束针对“staging + 覆盖落表”类 ETL 函数。这些是约束，不是版式偏好。

- 会话临时表必须可重复创建：`CREATE TEMPORARY TABLE` 前先 `DROP TABLE IF EXISTS`；调用方事务
  允许时加 `ON COMMIT DROP`（它在事务结束时删除，后续语句需仍在同一事务内）；**这是新代码的选项，
  改写既有函数时保持原清理方式**。临时表按会话隔离，
  不同会话不会互相看见；风险在同一会话内的重复/嵌套调用、失败分支残留，以及连接池复用。
  在证明单会话独占之前，一律假设两次调用可能共用一个会话。
- `DELETE` + `INSERT` 是一对**作用域**，不是两条独立语句。必须证明删除谓词覆盖插入可能产生的
  全部行，或明确写出 staging 过滤丢掉了哪些行。无谓词 `DELETE FROM <表>` 需要批准的例外理由。
- 删除范围要按**业务范围**核对，而不只是日期区间：同一目标表可能被多个 `p_type` 分支、多个
  省份或多个粒度写入，staging 也可能只补回部分月份/部分维度。整表刷新必须列出它覆盖的业务键
  与时间片，否则"可按区间重跑"只是函数级声明，不是目标表级保证。
- 原子性：函数体没有显式事务控制。`DELETE` 后 `INSERT` 抛异常且未被捕获时，异常会中止调用的
  （子）事务，已删除的行随之回滚。PL/pgSQL 的 `EXCEPTION` 块本身是子事务，块内捕获会回滚块内
  全部语句。真正的风险是：把 `DELETE` 放在块外、把易失败的 `INSERT` 放在块内吞掉异常后返回成功，
  此时删除可能随外层提交，而插入被回滚；或删除范围大于可重建范围。不要把它简化成"抛异常必然
  丢数据"或"吞掉外层异常就会提交删除"。
- "返回成功"不等于"写入了行"，但也不等于"必须写入行"。若契约需要区分"本次无数据"与"失败"，
  用 `GET DIAGNOSTICS ... ROW_COUNT` 或落表后计数来兑现；0 行本身不是错误，不要无条件要求
  行数校验。
- 可重跑性必须按**整次调用**声明：日期区间、业务范围、目标表、残留临时表、以及回滚不会撤销的
  序列副作用。
- 动态 SQL 落表至少要为一次代表性参数捕获生成的语句文本；只看构造代码的 diff 看不出实际执行了什么。

## 非 PostgreSQL 目标

本技能默认目标为**原生 PostgreSQL 12+**。仅当用户显式指定 Greenplum 或输入出现其专属构造时，
才切换为 Greenplum 兼容判定。Greenplum 专属构造包括 `DISTRIBUTED BY` /
`DISTRIBUTED RANDOMLY`、`SPLIT DEFAULT PARTITION`、`EXCHANGE PARTITION`、`pg_partition_rule`、
`pg_partitions`、`WITH (appendonly=true)`。

- 不得在未说明的情况下把 Greenplum DDL 翻成 PostgreSQL 声明式分区。
- 不得把 Greenplum 的分布、倾斜、append-optimized 假设带进原生 PostgreSQL 建议；临时表 CTAS 与
  膨胀行为在两边不同。
- 反向同样成立：仅在针对 GP 时注意版本差异——GP 5/6 分别基于 PG 8.3/9.4，
  GP 7 基于 PG 12；CTE 内联与 `[NOT] MATERIALIZED` 控制在原生 PG 12+ 可用，但 GP 5/6 的 CTE
  恒物化，GP 7 即使接受语法也受 ORCA 影响。索引可用性、分区裁剪、`ANALYZE` 采样与统计、
  `EXPLAIN` 输出格式（slice/segment）都与社区 PG 不同——索引和改写建议必须由用户在目标 GP 版本上
  验证，不能套用原生 PG 的计划结论。
- 读 `db_*` 旧 schema 的代码可能依赖外部或加载专用 schema；生成 SQL 时不要臆造、改名或"规范化"
  这些名字。

## 性能评审默认值

- 语义允许时，优先一条集合式语句，而不是逐行 SQL。
- 把循环、重复查询、过滤列上的函数、隐式 cast、`SELECT *`、无界结果集、不必要的异常块当作
  静态评审信号——不是慢的证明。
- 本技能不执行 `EXPLAIN`，也不连接数据库。需要计划或耗时结论时，由用户在代表性数据与参数上
  执行，并把快照与结果贴回来；本技能只给待验证项。
- 计划形状不能证明吞吐、锁竞争、WAL 量、膨胀或尾延迟；这些需要负载或统计工具。
- 比较方案时保持同一数据快照、统计信息状态、参数、PostgreSQL 版本与缓存条件。跨大版本或
  跨引擎（PostgreSQL ↔ Greenplum）的比较不成立。

## 输出语言

跟随用户语言。数据库、schema、索引、负载或版本信息缺失时，列出缺失输入，不要编造。
