# 重写协议

1. 先声明要保留的契约：签名、结果形态、NULL 行为、错误、权限、volatility、事务边界、副作用。
2. 把每项改动分类：纯版式、静态风险缓解、行为/性能变更。
3. 纯版式改动给 unified diff，并说明 SQL 结构与外部行为未变。
4. 性能改动给出原/新 SQL 形状、对索引/数据/负载的假设。每项性能陈述使用 Skill 的一个证据标签：`static-risk`、`inferred`、`plan-required`、`workload-required` 或 `not verified`；未实测不得声称更快。
5. 默认不改公共接口：函数名、参数名/顺序/类型、返回类型、volatility、异常文本、权限属性。
   确需改动时单独列出并取得明确同意——"不静默"不是标准；改了就是接口变更，可能破坏调用方。
6. 保留有意的例外，并逐条列出，不要把它们藏进"更干净"的代码里。

只给出更漂亮的 SQL、却不说明哪些没验证，视为未完成。

## 最小改动原则

改写是修复，不是重构。以下四条按顺序约束改动范围：

- **只改必要的地方**。能改 5 行就不要重排 500 行；纯格式重排单独一次提交，不和语义改动混在一起。
- **不引入原逻辑不需要的变量、常量、循环或分支**。每新增一个状态变量，必须能指出它对应哪条
  规则、解决了哪个具体问题；说不出就不要加。
- **不改变选择语义**。增量窗口的基准时间、上下界、过滤条件，没有明确批准就保持原样；觉得需要
  收紧时写成建议，由用户决定。
- **不做未经要求的结构重构**。分片、批处理、拆函数、改签名都属于结构变更，需要单独批准。
- **不动临时表的生命周期**。既有函数的 `ON COMMIT DROP`、显式 `DROP`、依赖会话结束，
  都是作者选择过的收尾方式；不要因为“更规范”就加 `ON COMMIT DROP`——它会把表的存活期
  从会话缩短到事务，属于行为变更。

判断标准很简单：把 diff 给原作者看，如果他需要花时间理解"为什么动这里"，就说明改多了。

## 必须原样保留的三样东西

这三样看起来像"待清理的痕迹"，实际是运维契约的一部分，改写时不得删除或改写：

- **调用示例注释**，例如 `/*select dwd.f_demo(1,'2026-01-01','2026-10-01')*/`。它记录了实际调用
  参数与顺序，是排障和交付验收的入口。
- **DDL 前导形态**：`CREATE ... ("p_flag" int4, ...) RETURNS "pg_catalog"."int2" AS $BODY$` 这类
  从 `pg_get_functiondef` 导出的写法，包括引号标识符、`int4`/`varchar`/`int2` 类型名与 `$BODY$`
  标签。改成 `smallint`、`character varying` 或 `$function$` 只会让下次导出产生无意义 diff。
- **原作者署名**：`*author` 保留原值，不替换为团队名或占位符。

## 落表型 ETL 函数的契约清单

落表型 ETL 函数的契约比签名宽得多。重写前逐项确认：

- [ ] 每个位置的参数含义，尤其是分派键 `p_type` 与模式标志 `p_flag`（内部窗口 vs 显式日期区间）。
      两者都会改变删除范围。
- [ ] 状态码语义：`0` 成功、`-1` 参数异常。原函数里产生 `-1` 的校验是否存在？重写是新增还是删掉了它？
      注意保留原有的成功/参数异常语义：原函数是否有 `IS NULL` 校验、是否真的执行 `RETURN -1`。
      同时注意 0 行可以是合法结果（空区间、源表无增量）；不要用 `ROW_COUNT > 0` 判成功，也不要在
      原函数没有该校验时擅自新增“无数据即失败”。
- [ ] 目标表，以及每次覆盖的精确谓词。把删除从"某日期切片"扩大为"整表"是行为变更，不是清理。
      按**业务范围**核对：同一目标表可能被多个 `p_type`、多个省份或多个粒度写入。
- [ ] 临时表：名字、创建顺序、后续分支是否依赖它。临时表按会话隔离；重点是同一会话内的重复/
      嵌套调用与失败分支残留，不是跨会话并发。
- [ ] 异常文本。`RAISE EXCEPTION '<fn>: %', SQLERRM` 内嵌函数名；调用方若按文本匹配，必须保持稳定，
      并说明 `SQLSTATE` 与 `DETAIL` 已经丢失。
- [ ] 回滚不会撤销的副作用：序列、identity、外部调用、运维依赖的 `raise info` 输出。
- [ ] 对 `db_*` 旧 schema 或兄弟函数的读取——这些是依赖，不是笔误。
- [ ] 调用示例注释、DDL 前导形态、`*author` 三样是否原样保留。
- [ ] `coalesce` 兜底、`INTERVAL` 时间窗、日期字面量与区间边界改写：会改变 NULL 和边界语义
      （哨兵值、右开/闭区间、`date` 与 `timestamp` 混用），按行为变更处理，必须做新旧结果对比。

## 验证边界

每项改动都要说明落在下表的哪一列：

| 构造 | 静态可证 | 必须执行才能证 |
|---|---|---|
| 动态 SQL 文本 | 构造模板与谓词形状 | 给定 `p_type`/`p_flag` 时实际执行的文本；日期插值的引号与类型行为 |
| 新增 `USING` / `format('%I')` | 绑定确实替代了拼接 | 错误文本、NULL 处理、计划变化、畸形输入行为 |
| 临时表 | 创建顺序、drop 点、作用域 | 同一会话内重复/嵌套调用、失败分支后的残留复用、临时文件量 |
| `DELETE` + `INSERT` | 目标表与谓词文本 | 删除范围是否等于插入范围、staging 过滤丢掉的行走哪、异常向外抛 vs 被内部吞掉后各留下什么状态 |
| `coalesce` / 日期 / 时间窗改写 | diff 里的表达式与原表达式 | NULL、空值、区间端点、时区与类型转换后的结果是否逐行一致 |
| 新增 `ANALYZE` / 索引 | diff 里有这个动作 | 计划与加载时间是否真的改善、与 autovacuum 的交互；GP 5/6 的索引/统计行为与现代 PG 不同，需由用户在目标版本验证 |
| 行数 / 成功标志 | 是否存在校验 | 校验阈值是否匹配生产行数；0 行是否合法 |

对落表型 ETL 函数做行为保持式重写时，以下验证由用户在目标库执行，本技能不代跑：

1. 同一快照、同一参数跑新旧两版，放在会回滚的事务里。
2. 对比目标切片行数与双向 `EXCEPT`（或校验和）。
3. 用失败参数重跑，确认目标表未被改动；若异常被函数内部吞掉，要单独检查是否出现"删了没补"。
4. 同一会话连调两次，暴露临时表冲突。
5. 由用户对最重的语句执行 `EXPLAIN (ANALYZE, BUFFERS)` 并提供耗时；拿不到时明确写“未测性能”。

## 引擎检查

本技能默认目标为**原生 PostgreSQL 12+**。仅当用户指定 Greenplum 或输入出现 `DISTRIBUTED BY`、
`SPLIT DEFAULT PARTITION`、`EXCHANGE PARTITION`、`pg_partition_rule`、`appendonly` 等构造时，
说明这段代码不可移植到原生 PostgreSQL。非标准 `RETURN EXCEPTION` 也不是标准 PL/pgSQL——不要在
PostgreSQL 代码里复现，也不要静默“修好”：应说明原写法在目标引擎上不可能按原样运行。

若目标显式为 GP：GP 5/6 分别基于 PG 8.3/9.4，GP 7 基于 PG 12。CTE 内联与 `[NOT] MATERIALIZED`
在原生 PG 12+ 可用，但 GP 5/6 的 CTE 恒物化，GP 7 即使接受语法也受 ORCA 影响。索引、分区裁剪、
`ANALYZE` 统计与 `EXPLAIN` 输出（slice/segment）都不同：不要把原生 PG 的 CTE 内联或索引结论直接套到
GP，索引与改写建议应由用户在目标 GP 版本上验证。
