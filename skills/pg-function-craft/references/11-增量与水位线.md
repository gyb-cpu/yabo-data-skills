# 增量更新与水位线

本文件定义“按更新时间（`update_time`）做增量”的规则，与 `00-风格与边界.md` §4 的“按业务日期切片”
并列。两种模式解决不同问题，不能互相替代。

## 0. 两种增量模式

| 模式 | 增量键 | 适用 | 重跑 | 迟到修正 | 物理删除 |
|---|---|---|---|---|---|
| `date_slice` | 业务日期列（`target_date` 等） | 分区/按天落表，数据按天稳定 | 天然幂等 | **抓不到** | 抓不到 |
| `update_time` | 源表 `update_time` | 源端会回补历史日期、有逻辑删除 | 需回看窗重叠 | 能抓到 | **抓不到** |

选择依据是源端行为，不是个人偏好：源端会改历史日期的数据，就必须用 `update_time`；源端只追加
当天数据，`date_slice` 更简单、更好重跑。

## 1. INC-01 `MUST` 增量模式必须显式声明

每个落表函数在头部或契约清单里写明三件事：

- 增量模式（`date_slice` / `update_time` / `full`）；
- 增量键（哪个业务日期列，或哪个 `update_time` 列）；
- 回看窗长度及其依据。

没有声明时，审查按“模式不明”处理，不得默认它是幂等的。

## 2. INC-02 `MUST` 回看窗是参数，不是散落的常量

回看起点应由参数或配置给出：

- `v_lookback := p_lookback_days`，或从任务配置表读取；
- 禁止在多支函数里各写一个 `CURRENT_DATE - INTERVAL 'N days'` 并且 N 不一致——同一批函数里
  1 天与 2 天并存、却没有一处说明依据，等于把“源端最大迟到”藏进了魔法数字。

回看窗长度的依据必须能写成一句话：**最大迟到时长 + 调度间隔 + 安全余量**。

## 3. INC-03 `MUST` 回看窗上界：新代码必须，改造既有代码需批准

只用 `update_time >= v_lookback` 是“开区间向未来延伸”，会把本批执行期间新提交的行也卷进来，
也会让回看范围随停机时间无限增长。新写的函数必须写成半开区间：

```sql
WHERE
    a.update_time >= v_lookback
    AND a.update_time < v_batch_ts
```

**改造既有函数时**，加上界会缩小选择范围，属于语义变更：写出建议、说明影响，由用户批准后再改；
不得默认为“更正确”而直接加。

`v_batch_ts` 的取值规则：

- 由调用方传入时，用调用方的批次时间；
- 函数内自取时，用 `clock_timestamp()`，**不要用 `now()`**：`now()` 是事务开始时间，早于
  “已提交但晚于事务开始”的行，用它会漏数（时间语义见 `09-工程与函数结构规范.md` ENG-23）；
- 同一批内只取一次，不要把 `clock_timestamp()` 写在多张源表的子查询里，否则各源表上界不同。

## 4. INC-04 `MUST` 业务日期区间从增量键推导，不靠猜

`update_time` 只回答“哪些行变了”，落表仍按业务日期覆盖。因此必须从变更行反推业务日期：

- 默认稀疏增量必须按 `INC-14` 用 `array_agg(DISTINCT ...)` 收集实际变更日期数组 `v_changed_dates date[]`，避免把未变更的中间空洞日期带入覆盖范围：

```sql
SELECT
    array_agg(DISTINCT a.target_date) FILTER (WHERE a.target_date IS NOT NULL)
INTO v_changed_dates
FROM
    demo.src_daily AS a
WHERE
    a.update_time >= v_lookback
    AND a.update_time < v_batch_ts;
```

- `min/max` 连续区间推导（`SELECT min(a.target_date), max(a.target_date) INTO v_start_date, v_end_date ...`）仅用于确认业务连续覆盖或显式回溯区间场景，不作为默认稀疏增量模板；
- 多张源表时，稀疏集合用 `UNION` 合并各自变更日期后再 `array_agg(DISTINCT ...)`，连续区间场景用 `UNION ALL` 合并各自 `min/max` 后再在外层取整体 `min/max`；
- 源表清单用数组参数 + `unnest`，或用字面量写死并逐条核对；不要用“逗号分隔字符串 +
  `string_to_array`”再拼 `FORMAT` 的方式生成 SQL（见 INC-10）；
- 推导结果为空（`v_changed_dates IS NULL OR array_length(v_changed_dates, 1) IS NULL`，或连续区间 `v_start_date IS NULL`）时按 INC-05 处理。

## 5. INC-05 `MUST` 禁止用哨兵日期表示“无数据”

`COALESCE(min(...), '2099-01-01')` 再判断 `IF v_start = '2099-01-01'` 是典型写法，但它把
“没有数据”编码成一个合法日期：一旦业务真出现该日期就会误判，比较与区间算术也会带上它。

规范写法是保留 `NULL`：

```sql
IF v_start_date IS NULL THEN
    RETURN 0;
END IF;
```

需要区分“无变更”与“变更了但业务日期为空”时，两者分别用一个布尔标志记录，不要共用哨兵值。

检查器对 `'2099-01-01'` 一类哨兵日期报 `INC-05`。

## 6. INC-06 `MUST` 删除谓词与插入谓词同源

覆盖式落表必须保证“删掉的范围”就是“重新写入的范围”：

- `DELETE` 的业务日期条件与 `INSERT ... SELECT` 的筛选条件必须来自同一对变量
  （`v_start_date` / `v_end_date`）；
- 不得一边用推导出的区间、一边用原始 `p_start_date` / `p_end_date`——参数与推导值不等时，
  会删掉没补回的行；
- `DELETE` 的执行范围要在交付物里写清楚，不写“按日期删除”这种概括（见 `01-基线规范.md`
  的“落表路径验证”与 `AP-03`）。

## 7. INC-07 `MUST` 声明“逻辑删除可捕获、物理删除不可捕获”（写在审查报告，不写进函数头）

- 源表有 `deleted` / `isdel` / `is_deleted` 一类标记列时，逻辑删除通常会刷新 `update_time`，能被回看窗捕获。
  **从 `update_time` 推导变更业务日期（`v_changed_dates` / `v_changed_months` / `min/max`）时，禁止过滤 `deleted = 0`（或 `is_deleted = 0`）**：否则被逻辑删除的行会在日期推导阶段被跳过，导致目标表对应业务日期不触发 `DELETE` + `INSERT`，从而在目标表继续残留已删除的过期行。
- `AND a.deleted = 0` 必须**只写在** `INSERT ... SELECT` 抽取查询中，与按变更日期执行的 `DELETE` 配合完成目标侧同步清理。
- 源端的物理 `DELETE` **不会**刷新任何时间戳，`update_time` 增量永远看不到它。这条写在审查
  报告或交付说明里就够了，**不要塞进函数头**（`*remark` 之类）——函数头只放调用者需要的契约。
  兜底方案：周期性全量对账，或按业务日期区间重刷。
- 反向也要注意：源端“先物理删除再插入”会改变主键但保留业务键，回看窗只能看到新插入的行，
  旧行不会被清理——这类源端必须配全量对账。

## 8. INC-08 `MUST` 声明 `update_time` 的可信前提

`update_time` 增量成立的隐含条件，必须在交付物里逐条确认：

- 该列由 `DEFAULT CURRENT_TIMESTAMP`、触发器或 ETL 写入显式维护；
- 应用层的 `UPDATE` 真的刷新了它——手写更新未刷新该列，会永久漏数；
- `COPY`、批量导入、`INSERT ... SELECT` 不绕过该列；绕过时要额外补一条“导入后回刷时间”的路径；
- 时钟源是数据库服务器时间，不是应用服务器时间；跨库比较时两边时钟要同步；
- 该列有可用的索引或分区裁剪条件，否则回看窗就是全表扫描（`PERF-29`、`plan-required`）。

任一条不成立时，降级为 `date_slice`，并把这个决定写进契约，不要在不可信的列上造假增量。

## 9. INC-09 `MUST` 回看窗重叠必须幂等

回看窗天然重叠：每次调度都把窗口内的日期整片重算。因此落表只能是**按业务区间覆盖**
（`DELETE` + `INSERT`，或分区交换），不能是追加：

- 禁止 `INSERT` 只追加不删除——重叠窗会写出重复行；
- 目标表有唯一键时，重复行会直接报错，这比静默重复更安全；
- 幂等声明按整次调用写，覆盖“日期窗、业务键、目标表、残留临时表、序列副作用”
  （`09` ENG-15）。

## 10. INC-10 `MUST` 多源表推导的写法要求

推导区间要拼动态 SQL 时：

- 标识符用 `format('%I', ...)`，值用 `USING` 或 `%L`，不得把表名、日期直接拼进字符串
  （`AP-01`、`ENG-08`）；
- 表清单优先用数组参数：`unnest(p_tables::text[])`，避免“逗号分隔字符串 + 解析”；
- 拼出的语句要能打印一次做核对，但生产日志只打长度或标识，不打整段 SQL（`AP-09`）；
- 推导语句本身也要有 `WHERE update_time >= ... AND update_time < ...`，否则推导范围与抽取范围
  不一致。

## 11. INC-11 `MUST` 首次全量与增量切换

- 全量跑完后，把“全量覆盖的业务日期上界”记为下一次增量的起点，或先跑一次覆盖最大迟到的
  大回看窗；
- 切换过程写在部署说明里；没有这一步，增量第一次运行会从空水位开始，看起来“没有数据”；
- 不允许用“把回看窗设成 10 年”代替全量，那会把一次调度变成全表扫描。

## 12. INC-12 `MUST` 证据边界

以下判断都是静态的，结论只能标对应标签：

| 判断 | 标签 | 说明 |
|---|---|---|
| 回看窗是否覆盖实际迟到 | `workload-required` | 需要源端迟到分布数据 |
| `update_time` 是否真被刷新 | `plan-required` | 需要看写入路径、触发器或应用代码 |
| 回看窗能否走索引 | `plan-required` | 需要 `EXPLAIN` |
| 删除范围是否等于重建范围 | `static-risk` | 读谓词即可判断，但结果仍需对账 |

本技能不连库，不执行 `EXPLAIN`；以上都不能写成“已验证”。

## 13. INC-13 `MUST` 推导区间可能暴涨时要评估分片（属于结构变更，改造需批准）

回看窗命中的行可能带着很久以前的业务日期——一次历史数据修正，就会让 `min/max` 推导出
跨越数年的区间。直接按这个区间 `DELETE` + `INSERT`，单次调用会重算多年数据：事务过长、
WAL 暴涨、锁持有时间不可控，失败时回滚代价极高。

这不是精度问题，是可控性问题：结果可能仍然正确，但一次异常修正足以拖垮实例。

**分片是结构变更，不是默认动作。** 改造既有函数时，先给出区间分布证据与分片方案，由用户批准
后再实施；不得因为“区间可能很大”就擅自把单条 DML 改成循环。

三种处置方式，契约里写清选哪一种：

- 按业务日期把推导区间切成固定粒度（天/月）逐片处理；
- 对区间宽度设上限（例如 31 天），超出时拆成多次调用并记录；
- 只允许回看窗内的业务日期，超出部分单独告警并交人工确认。

拆片时每一片仍要满足 INC-06 与 INC-09：删除谓词与插入谓词同源、单片可重跑。

## 14. INC-14 稀疏变更集合与路径复用

当增量命中的业务日期/月不连续时，`min/max` 只能作为告警或统计信息，不能单独决定覆盖范围。函数必须保留去重后的实际变更集合，或在跨语句需要冻结结果时物化该集合；`DELETE` 与 `INSERT` 使用同一集合。显式区间分支仍使用调用方的连续区间，不能被稀疏增量规则改写；逻辑删除仍沿用原有捕获和目标同步语义。

ETL 改写交付物先给出“函数、执行模式、源表、业务键/粒度、过滤窗口、关联/聚合、物化点、目标表”的读取与物化路径。相同源表和窗口的过滤、关联、聚合只保留一份；主源按业务键有有效值时，真实 `0` 也阻断备用源聚合，只保留备用源独有键和既有冲突规则。公共关联优先在低粒度完成后再展开；只转存一次且没有复用、写入隔离或独立统计理由的临时表应合并。

`INC-14` 的静态验收必须包含：稀疏日期集合、显式区间、逻辑删除、主源为 `0`、仅备用源、主备冲突、空集合。离线样例只核对集合、选择和粒度不变量，不产生计划、吞吐或速度结论；性能证据仍按 `PERF-47`～`PERF-51` 标记。

## 15. INC-15 `MUST` 新驱动源必须同步进入增量日期推导

当按目标业务键构造驱动集合时，新增并入 `UNION` 的源必须同时进入 `update_time` 增量的业务日期推导路径（或进入等价的实际变更日期集合）。只把源加入 `clear_key` 等驱动集合、却不加入水位线扫描，会导致该源独有业务键永远不触发重算；只加入水位线而不加入驱动集合，则仍会在重建时漏行。

该规则只适用于能独立提供目标业务键的源。纯补列源没有独立业务键时，不因存在 `LEFT JOIN` 就加入驱动集合或增量日期推导。

静态验收至少对照两张清单：

- 驱动键源清单：所有能独立提供日期、主体、交易单元等目标键的源；
- 增量日期源清单：所有参与 `update_time`/变更日期集合推导的源。

两张清单应一致；若不一致，按 `INC-15` 标记并补离线键集合差集探针。该判断不产生执行计划或负载结论。

## 16. 规范写法（模板）

```sql
CREATE OR REPLACE FUNCTION demo.f_demo_daily_settlement_d(
    p_flag integer
    , p_start_date date
    , p_end_date date
    , p_lookback_days integer
)
RETURNS integer
LANGUAGE plpgsql
SECURITY INVOKER
SET search_path = ''
AS $function$
/*****************************************************************
*name       : demo.f_demo_daily_settlement_d
*function   : 演示按更新水位线稀疏增量或显式区间落表
*input      : p_flag 0=增量 1=按日期区间, p_start_date=开始日期, p_end_date=结束日期, p_lookback_days=回看天数
*output     : -1参数异常, 0正常
*increment  : update_time 水位线，半开区间 [clock_timestamp()-p_lookback_days, clock_timestamp())，按 v_changed_dates 稀疏集合覆盖
*author     : <team>
*CreateDate : 2026-01-01
*UpdateDate : 2026-11-27
******************************************************************/

DECLARE
    v_batch_ts timestamp := clock_timestamp();
    v_lookback timestamp;
    v_changed_dates date[];
    v_state text;
    v_msg text;
BEGIN
    -- 1. 参数校验
    IF p_flag IS NULL OR p_flag NOT IN (0, 1) THEN
        RETURN -1;
    END IF;

    IF p_lookback_days IS NULL OR p_lookback_days < 0 THEN
        RETURN -1;
    END IF;

    IF p_flag = 1 AND (p_start_date IS NULL OR p_end_date IS NULL OR p_start_date > p_end_date) THEN
        RETURN -1;
    END IF;

    -- 2. 按执行模式覆盖目标表
    IF p_flag = 0 THEN
        v_lookback := v_batch_ts - (p_lookback_days || ' days')::interval;

        -- 不在此处过滤 deleted = 0：逻辑删除行也必须触发目标表对应日期重算，
        -- 否则目标表会继续残留已被源端逻辑删除的历史数据
        SELECT
            array_agg(DISTINCT a.target_date) FILTER (WHERE a.target_date IS NOT NULL)
        INTO v_changed_dates
        FROM
            demo.src_daily AS a
        WHERE
            a.update_time >= v_lookback
            AND a.update_time < v_batch_ts;

        IF v_changed_dates IS NULL OR array_length(v_changed_dates, 1) IS NULL THEN
            RETURN 0;
        END IF;

        DELETE FROM demo.dwd_daily_settlement
        WHERE
            target_date = ANY(v_changed_dates);

        INSERT INTO demo.dwd_daily_settlement (
            target_date
            , company_name
            , energy
        )
        SELECT
            a.target_date
            , a.company_name
            , sum(a.energy)
        FROM
            demo.src_daily AS a
        WHERE
            a.target_date = ANY(v_changed_dates)
            AND a.deleted = 0
        GROUP BY
            a.target_date
            , a.company_name;
    ELSE
        DELETE FROM demo.dwd_daily_settlement
        WHERE
            target_date >= p_start_date
            AND target_date <= p_end_date;

        INSERT INTO demo.dwd_daily_settlement (
            target_date
            , company_name
            , energy
        )
        SELECT
            a.target_date
            , a.company_name
            , sum(a.energy)
        FROM
            demo.src_daily AS a
        WHERE
            a.target_date >= p_start_date
            AND a.target_date <= p_end_date
            AND a.deleted = 0
        GROUP BY
            a.target_date
            , a.company_name;
    END IF;

    RETURN 0;

EXCEPTION
    WHEN OTHERS THEN
        GET STACKED DIAGNOSTICS
            v_state = RETURNED_SQLSTATE
            , v_msg = MESSAGE_TEXT;
        RAISE EXCEPTION '增量落表执行失败: %', v_msg
            USING ERRCODE = v_state;
END;
$function$;
```

模板要点：

- 入口完整校验 `p_flag`（仅 `0` 或 `1`）、`p_lookback_days`（非空且 `>= 0`），以及 `p_flag = 1` 时的 `p_start_date`/`p_end_date` 非空与区间顺序，参数异常返回 `-1`；
- 显式声明 `SECURITY INVOKER` 与 `SET search_path = ''` 并全限定对象名，防止搜索路径劫持；
- 上界 `v_batch_ts` 只取一次，用 `clock_timestamp()`；
- `p_flag = 0` 默认按 `array_agg(DISTINCT a.target_date) FILTER (WHERE a.target_date IS NOT NULL)` 收集稀疏变更集合 `v_changed_dates date[]`，`DELETE` 与 `INSERT` 共用 `= ANY(v_changed_dates)`；`p_flag = 1` 显式区间分支按连续参数区间覆盖；
- 空集合用 `v_changed_dates IS NULL OR array_length(v_changed_dates, 1) IS NULL` 判断并提前返回 `0`，不引入哨兵日期；
- 变更日期推导查询不过滤 `deleted = 0`，确保逻辑删除行也能触发目标日期清理；`AND a.deleted = 0` 只写在 `INSERT ... SELECT` 抽取查询中；
- `EXCEPTION WHEN OTHERS` 用 `GET STACKED DIAGNOSTICS` 提取 `RETURNED_SQLSTATE` 与 `MESSAGE_TEXT` 并以 `USING ERRCODE = v_state` 重抛，不把函数名硬编码进异常消息。
