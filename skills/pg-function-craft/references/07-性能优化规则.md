# 性能优化规则（参考来源整理）

本文件是「性能优化层」的规范来源接入，整理自公开的 PostgreSQL 社区指南，用于**审查与生成时的
提示**，不针对任何个人或语料，也不是性能实测报告。

- 规则性质：`normative`（规范要求）；来源类型：`reference`（外部参考）。
- 本文件**不产生 `observed` 结论**，也不附带任何语料计数、置信度或证据边界。
- 本文件**没有运行**任何数据库、`EXPLAIN`、`pgFormatter`、`SQLFluff` 或其他外部审查工具；
  不声称任何写法“已实测更快”“已验证性能”。文中出现的倍数、百分比若来自来源，只作为来源主张
  转述，不是本技能的测量结果。
- 默认不连库：性能分析止于静态 SQL。没有用户提供的真实执行计划与负载数据时，结论只能落在
  `static-risk`、`inferred`、`plan-required`、`workload-required` 或 `not verified`；不得用“静态检查通过”暗示性能已确认（见 `00-风格与边界.md` 第 2 节）。
- 与 `references/01-基线规范.md`「性能评审默认值」冲突时，以 `01` 的安全与正确性约束为准；
  与项目已确认的书面约定冲突时，以项目约定为准；本文件只补充“怎么判、需要什么证据”。

### 0.2 证据分三段，标签有五个

性能陈述按“能看到什么证据”分三段，但落笔时只能使用五个既有标签之一（定义见
`README.md` 第 7 节）。两者是粒度与词汇的关系，不是两套体系。

| 段位 | 允许回答的问题 | 对应标签 | 典型手段 | 不能回答 |
|---|---|---|---|---|
| A. 静态风险 | 代码形状/DDL/目录信息是否提示风险 | `static-risk`（必要时 `inferred`） | 读 SQL、读 `pg_indexes`、`pg_stats`、`pg_proc`、表 DDL | 快慢、计划形状、锁等待、吞吐 |
| B. 执行计划（用户侧） | 计划是否按预期走索引、连接顺序、估算行数、GP 的 motion | `plan-required`（只作待验证项，不升级为实测结论） | `EXPLAIN`、`EXPLAIN (ANALYZE, BUFFERS)`（由用户在目标库执行；本技能不执行） | 吞吐、并发、WAL、膨胀、尾延迟 |
| C. 负载验证 | 在真实并发/数据量下的吞吐、锁、WAL、膨胀、尾延迟 | `workload-required` | `pg_stat_statements`、`pg_stat_activity`、`pg_locks`、压测、膨胀测量、日志 | 不能外推到其他数据分布/版本/引擎 |

写作要求：

- 只到 A 档时，只能写“存在风险，需要 B/C 档验证”，不能写“更慢/更快”。
- 到 B 档时，必须写明快照：PostgreSQL/Greenplum 版本、表行数与统计信息时间、参数、缓存状态、
  是否 `ANALYZE`、是否同一数据快照。
- 到 C 档时，必须写明负载模型（并发数、持续时间、读写比）与采集窗口；单次手工执行不算负载验证。
- 跨大版本（如 PG 12 ↔ PG 15+ 或 PG 9.4）或跨引擎（PostgreSQL ↔ Greenplum）的计划结论不可互相外推。

### 0.3 版本与方言前提

本技能默认目标基线为**原生 PostgreSQL 12+**；PostgreSQL 9.4 / Greenplum 6.6（内核基于 PG 9.4）为按需启用的可选兼容模式，仅在显式声明时降级。标记约定：

- `[PG 12+]`：默认原生 PG 12+ 基线可用（不额外假设 PG 13+ 独占特性）。
- `[13+]`、`[14+]`、`[15+]`：高于默认 PG 12+ 基线的新特性，使用前须确认目标 PG 版本。
- `[GP-6.6]` / `[GP-待验证]`：仅当显式指定目标为 Greenplum 6.6 时适用；GP 运行行为需在目标集群确认，不得按社区 PG 推断。
- `[待验证]`：来源或版本文档未能确认，只能作为待办，不得写成结论。

| PERF-51 | ETL 审查交付物必须先列函数、执行模式、源表、业务粒度及读取/物化路径，并以离线样例核对边界 | ETL | `not verified` | 不产生运行时性能结论 |
| PERF-52 | 多源宽表的驱动键集合必须并入所有能在目标粒度独立提供业务键的源；仅补列且不能独立提供业务键的源不参与驱动 | ETL 正确性 | `static-risk` | `[PG 12+]`；业务键粒度由输入确认 |
| PERF-53 | 固定高粒度目标表的 24→96 等粒度转换应在各源路径先完成并复用；最终层只做统一业务键 × 目标粒度关联，不重复展开或逐字段拆分 | ETL 路径 | `static-risk` + `plan-required` | `[PG 12+]`；目标粒度与源粒度由输入确认 |
| PERF-54 | 合同派生表应在聚合前下推日期窗口和业务域交易单元过滤；不能先全表按 `contract_id` 聚合，再仅在外层过滤 | ETL 路径 | `static-risk` + `plan-required` | `[PG 12+]`；过滤列与业务域由输入确认 |

### 1.1 驱动键覆盖（PERF-52）

多源合并的 `INSERT ... SELECT` 先构造目标业务键集合，再把各源按键关联到该集合。凡某源能独立提供目标粒度所需的日期、主体、交易单元等业务键，就必须把该源的键并入驱动集合（通常用 `UNION` 或等价集合运算）；`LEFT JOIN` 只能补列，不能承担新增业务键的职责。

这不是“所有 `LEFT JOIN` 都要变成驱动源”：没有目标键维度、只能提供公共价格或其他补充属性的源，仍是纯补列源。例如公共价格表不能仅因存在 `LEFT JOIN` 就被要求铺底。判定前必须先确认该源是否能在目标粒度独立产出完整业务键。

静态探针可用来证明驱动键缺口：

```sql
WITH lt AS (
    SELECT DISTINCT
        a.target_date
        , a.company
        , a.transaction_unit
    FROM supplement_source AS a
    JOIN dim_unit AS d
        ON d.unit_name = a.transaction_unit
)
    , base AS (
        SELECT target_date, company, transaction_unit FROM source_a
        UNION
        SELECT target_date, company, transaction_unit FROM source_b
)
SELECT count(*)
FROM (
    SELECT * FROM lt
    EXCEPT
    SELECT * FROM base
) AS missing_key;
```

结果大于 0 说明存在只由补列源提供、但目标表不会产出的业务键。执行前后还应按目标日期对比行数与稳定指纹；本技能不执行该 SQL，探针结果属于用户侧证据。

### 1.2 目标粒度前置展开（PERF-53）

当目标表固定为更高时间粒度（例如 96 点），且源端或中间层仍是 24 点时段，先在各自源路径完成 24→96 映射，再让后续聚合、主体映射、驱动键和公共关联复用同一份目标粒度明细。最终层只负责统一业务键与 96 时段的关联和列装配。

静态风险信号：

- 多个源临时表/CTE 都先聚合到 24 点，最后才 `CROSS JOIN` 时间维表扩展到 96 点；
- 最终 `SELECT` 对每个指标重复写 24→96 的 `CASE`、四拆分或相同时间映射；
- 同一源的主体映射、驱动键、日汇总或合同类型聚合分别从不同的 24 点中间层重新展开；
- 已经有目标粒度明细，却在最终层再次与时间维表关联。

整改方向是把转换前置到源路径并复用同一目标粒度结果；最终层不得再次展开。该规则不要求把所有源强行铺成全 0 行，也不改变 `PERF-52` 对驱动键源与纯补列源的区分。没有执行计划时只能标 `static-risk` / `plan-required`，不能声称已变快。

### 1.3 合同派生过滤下推（PERF-54）

合同基础信息派生表在 `GROUP BY`/`max(contract_cycle)` 前，必须先限制目标日期窗口和业务域交易单元。典型条件包括：

```sql
WHERE
    b.trade_end_date >= v_start_date
    AND b.trade_start_date <= v_end_date
    AND b.purchaser_unit IN (
        SELECT d.unit_name
        FROM demo.dim_unit_scope AS d
        WHERE d.domain_type = '<business_domain>'
          AND d.region = '<target_region>'
    )
```

外层仍保留 `purchaser_unit = c.unit_name` 与 `c.target_date BETWEEN b.trade_start_date AND b.trade_end_date` 的精确匹配。只在外层 `ON` 中过滤，不能替代派生表内部的窗口和业务域过滤；它会让派生表先对无关合同全表聚合。没有计划与真实数据量时，只能标 `static-risk` / `plan-required`。

## 2. 索引与访问路径

### 2.1 何时考虑索引（PERF-01）

静态信号（只到 A 档）：

- `WHERE`、`JOIN ... ON`、`ORDER BY`、`GROUP BY` 的高频列没有对应索引。
- 过滤列选择性高（返回行占比低），但计划仍可能因统计过期走顺序扫描。
- 外键引用列缺少索引：删除/更新父表时可能放大锁与扫描（社区常见建议，GP 上 `[GP-待验证]`）。

不能只凭“有 `WHERE`”就建索引。还要看：调用频率、返回行占比、表大小、写入频率、现有索引的
最左前缀能否复用、以及 GP 的分布键是否已经让扫描落在单 segment。

### 2.2 复合索引列序（PERF-02）

默认顺序：等值谓词列在前，范围谓词列在后，排序列尽量跟随。

```sql
-- 目标：WHERE status = 'pending' AND created_at >= p_start ORDER BY created_at
CREATE INDEX idx_orders_status_created
    ON demo.orders (status, created_at);
```

- 最左前缀：`(status, created_at)` 不能高效支撑只按 `created_at` 过滤的查询。
- 不要为了“一个索引走天下”把低选择性列放最左；能否走 index-only scan 还要看 §2.5。
- 索引列序是**结构决策**，不是排版；改写必须给用户侧 `EXPLAIN` 前后对比方案。

### 2.3 部分索引与表达式索引（PERF-03、PERF-04）

部分索引适合“查询总是带同一个稳定谓词”的场景：

```sql
CREATE INDEX idx_orders_pending
    ON demo.orders (created_at)
    WHERE status = 'pending';
```

- 谓词必须与查询谓词**可证明等价**；参数化谓词（`status = p_status`）通常无法稳定匹配。
- 部分索引会让规划器依赖该谓词；业务状态分布变化后要重新评估。
- 表达式索引要求表达式与查询中的写法**逐字同形**（包括 cast 与函数名）；大小写、`::numeric`
  与隐式转换都可能让索引失效。

```sql
CREATE INDEX idx_orders_dt
    ON demo.orders ((created_at::date));
```

- 表达式索引不是“给列套函数”的许可证；先确认业务是否应该存派生列。
- 表达式必须是 immutable；`now()`、`clock_timestamp()` 不能用于索引表达式。
- PG 12+ 默认可用；显式声明 GP 6.6 时表达式索引按 GP 文档可用，实际行为仍需在目标集群确认。

### 2.4 索引类型与版本门槛（PERF-05）

| 能力 | 最低版本 | PG 12+（默认） | 可选 GP 6.6 / PG 9.4 | 说明 |
|---|---|---|---|---|
| btree | 很早 | 可用 | 均可用 | `=`、`<`、`>`、`BETWEEN`、`IN`、`IS NULL` |
| 部分索引 | 7.4 | 可用 | 均可用 | 谓词稳定的查询 |
| 表达式索引 | 7.4 | 可用 | 均可用 | 表达式须与查询同形 |
| GIN（jsonb/数组/tsvector） | 9.4（jsonb） | 可用 | 9.4 可用；GP `[GP-待验证]` | `@>`、`?`、`?&`、`?\|`；GP 实际行为按目标集群确认 |
| GiST（范围/几何/KNN） | 较早 | 可用 | 9.4 可用；GP `[GP-待验证]` | 操作符类决定用途 |
| BRIN | 9.5 | **可用** | **不可用** | 大表时序场景；PG 12+ 默认可用 |
| `INCLUDE` 覆盖列 | 11 | **可用** | **不可用** | 非键列覆盖索引；GP / 9.4 用多列索引 |
| hash 索引 WAL-safe | 10 | **可用** | **不可用/不推荐** | PG 10+ WAL-safe；9.4 崩溃风险 / GP 停用 |
| `CREATE INDEX CONCURRENTLY` | 8.2 | 可用 | 9.4 可用；**GP 6.6 不支持** | PG 中不能在事务块/函数内执行 |
| `REINDEX CONCURRENTLY` | 12 | **可用** | **不可用** | PG 12+ 在线重建索引；GP / 9.4 用普通 `REINDEX`（持锁） |

来源中常见的“GIN 比 btree 快 10–100 倍”“部分索引小 5–20 倍”是来源主张；本技能不背书数值，
也不把它写进审查结论。本表只覆盖索引类型；**其他语法特性的版本事实见
`10-PLpgSQL语法与函数形态.md` §1.1**，本文件不另维护版本清单。

### 2.5 覆盖索引：`INCLUDE` 与多列索引（PERF-06）

- 默认基线 **PG 12+ 已支持 `CREATE INDEX ... INCLUDE (...)`**（`[11+]`），可把仅用于 `SELECT`/过滤返回的非键列放进索引页载荷而不扩大 B-tree 查找键；若目标显式为 GP 6.6 / PG 9.4，则退回多列索引：

```sql
-- PG 12+ 默认写法
CREATE INDEX idx_orders_status_created_inc_id
    ON demo.orders (status, created_at) INCLUDE (id);

-- 显式 PG 9.4 / GP 6.6 兼容写法
CREATE INDEX idx_orders_status_created_id
    ON demo.orders (status, created_at, id);
```

- index-only scan 还依赖 visibility map：新写入/未 `VACUUM` 的页面仍要回表；因此“覆盖索引”
  不等于“零堆访问”，属于 `plan-required` + `workload-required`。
- `INCLUDE` 与多列索引都会增大写放大与体积，是否值得必须用 §8 的方法验证。

### 2.6 索引的代价（PERF-07）

新增索引至少带来：每次 `INSERT/UPDATE/DELETE` 的索引维护、WAL 增量、缓存占用、规划时间、
`VACUUM` 负担与膨胀。审查时要求同时给出：

- 预期加速的查询与调用频率（B/C 档证据）；
- 写入路径的额外成本与可接受的维护窗口；
- 回滚方案（`DROP INDEX` 的锁级别，或 `DROP INDEX CONCURRENTLY` 是否可用）。

### 2.7 索引审查清单

- [ ] 索引列与查询谓词/排序列对应，且遵守最左前缀。
- [ ] 没有为低选择性列单独建索引却被当作万能索引。
- [ ] 部分索引谓词与查询谓词可证明等价。
- [ ] 表达式索引与查询表达式逐字同形。
- [ ] 仅当显式声明 PG 9.4 / GP 6.6 时检查未误用 `INCLUDE`、BRIN、`REINDEX CONCURRENTLY`。
- [ ] 新增索引的写放大与维护成本已评估（不能只写“加索引会更快”）。
- [ ] 若目标为 GP，已确认索引类型可用性，未把社区 PG 结论直接搬过去。

### 2.8 索引失效的排查顺序（PERF-29、PERF-30）

出现“明明有索引却没走”时，按下面顺序排查，每次只改一处：

1. 过滤列是否被函数、算术、拼接或 `::text` 包裹（`PERF-29`）。
2. 参数与列是否同一类型族；`date ↔ timestamp`、`text ↔ varchar` 的隐式 cast 是否发生（`PERF-30`）。
3. 复合索引是否命中左前缀（`PERF-02`）。
4. 部分索引的谓词是否与查询谓词可证明等价（`PERF-03`）。
5. 表达式索引是否与查询表达式逐字同形（`PERF-04`）。
6. `LIKE '%x%'`、非锚定正则是否使 B-tree 失效（`PERF-35`）。
7. 统计信息是否过期，估算行数是否与实际严重偏离（`PERF-08`、`PERF-41`）。

改写谓词时保持语义不变：`date_trunc('day', d) = p` 改成半开区间前，要确认时区与边界；
`col::text = p` 改成 `col = p::col类型` 前，要确认非法输入与舍入行为。计划只是结果，
语义正确性仍按 `references/01-基线规范.md` 判断。

### 2.9 唯一约束与唯一索引（PERF-38）

- 普通唯一性用约束：可被外键引用，错误信息带约束名；PG 内部仍由唯一索引实现。
- 软删除后复用同一业务键、或只对部分行唯一时，用带 `WHERE` 的唯一索引。
- 唯一约束/唯一索引会改变写入失败语义（`unique_violation`），重写时按行为变更处理。
- GP 的唯一约束必须包含分布键，否则可能无法创建；这是 GP 的建模约束，不是性能偏好。

### 2.10 未使用索引的删除决策（PERF-37）

- `pg_stat_user_indexes.idx_scan = 0` 只说明“统计以来没被扫描”，不说明以后不用。
- 删除前确认：统计是否被重置、覆盖的完整业务周期（月末/季末/年初）、是否有只读副本、报表或
  外部系统依赖该索引。
- 先在测试库删除并对比关键查询计划；生产删除按 C 档验证，并保留重建脚本与回滚窗口。
- GP 的索引使用统计与 segment 级行为 `[GP-待验证]`；不要用单机 PG 的 `idx_scan` 经验直接判断。

## 3. 统计信息与表维护

### 3.1 `ANALYZE`（PERF-08）

- 大批量 `INSERT`、`DELETE`、分区交换后，统计信息可能仍描述旧分布；先 `ANALYZE` 再解释计划。
- `ANALYZE` 可以在事务块内执行；`VACUUM` 不能（见 §3.3）。
- `pg_stat_user_tables` 提供 `last_analyze`、`last_autoanalyze`、`n_live_tup`、
  `n_dead_tup` 等列；不同小版本的列集合可能变化，使用前先 `\d+` 确认。
- 可选 GP 6.6 的分区表统计有额外规则（根分区/子分区），语法与传播行为 `[GP-待验证]`；
  不要假设对子分区 `ANALYZE` 会自动改善根分区的计划。

### 3.2 autovacuum（PERF-09）

- PG 12+ 支持表级 reloptions：`autovacuum_vacuum_scale_factor`、
  `autovacuum_analyze_scale_factor`、`autovacuum_vacuum_threshold` 等。
- 调参前先确认全局 `autovacuum` 是否开启、是否有长事务持有旧快照、是否有复制槽/逻辑解码阻碍回收。
- PG 12+ 默认可查 `pg_stat_progress_vacuum`（`[9.6+]`）与 `pg_stat_activity.wait_event`；若目标显式为 GP 6.6 / PG 9.4 则不可用，只能看 `pg_stat_activity.query` 与 `pg_stat_user_tables` 时间戳。

### 3.3 膨胀与回收（PERF-10）

| 手段 | 锁/代价 | PG 12+（默认）/ 可选 GP 6.6 | 适用 |
|---|---|---|---|
| `VACUUM` | 较弱锁，不重写表 | 均可用；不能进事务块/函数 | 回收死元组、更新 visibility map |
| `VACUUM FULL` | `ACCESS EXCLUSIVE`，重写表 | 均可用；GP 行为 `[GP-待验证]` | 严重膨胀且可接受停机 |
| `REINDEX` | 普通版阻塞写；`CONCURRENTLY` `[12+]` 不阻塞读写 | **PG 12+ 支持 `CONCURRENTLY`**；GP / 9.4 仅普通版 | 索引膨胀/损坏 |
| `pg_repack` 等外部工具 | 需额外安装与权限 | `[待验证]` | 在线重组，需单独评估 |

`VACUUM` 与 `CREATE INDEX CONCURRENTLY` 不能在函数内执行：函数总在事务中运行，这类语句会报错。
`ANALYZE` 没有这个限制。

### 3.4 GP 差异

- GP 的 AO（append-optimized）表与堆表在空间回收、`VACUUM`、`VACUUM FULL` 上的行为不同，
  具体以目标 GP 6.6 文档与用户侧验证为准 `[GP-待验证]`。
- GP 的 `ANALYZE` 采样、分区统计与社区 PG 9.4 不完全一致；用社区经验推断 GP 的统计质量不成立。
- GP 的 `EXPLAIN` 输出包含 slice 与 motion，不能直接套用社区 PG 的 `Seq Scan`/`Index Scan` 解读。

### 3.5 `fillfactor` 与 HOT（PERF-45）

- `fillfactor` 降低页面填充率，为 `UPDATE` 留空间；只有“频繁更新且不修改任何索引列”的堆表
  才可能受益于 HOT，从而减少索引维护与新页分配。
- 代价是表体积变大、顺序扫描页数增加；没有更新模式与膨胀数据时不要改。
- PG 12+ 支持表级 `fillfactor`；仅显式 GP 目标下 AO 表与列存不适用 HOT，不要把堆表经验套过去。

## 4. 写入路径

### 4.1 批量写入（PERF-11）

- 多值 `INSERT`（每批约数百到一千行，需用户侧验证）比逐条 `INSERT` 少往返；`COPY` 适合大批量导入。
- 函数内的 `INSERT ... SELECT` 优先于 `FOR` 循环逐行插入；循环只在分区 DDL、逐条修复等场景保留。
- 批大小不是越大越好：受 `work_mem`、WAL、锁、undo/回滚段与 GP segment 内存影响，属于
  `workload-required`。

### 4.2 消除 N+1（PERF-12）

```sql
-- 反例：循环里逐条查询
FOR v_id IN
    SELECT id FROM demo.users WHERE active
LOOP
    SELECT count(*) INTO v_cnt FROM demo.orders WHERE user_id = v_id;
END LOOP;

-- 改为集合式
SELECT
    u.id
    , count(o.id) AS order_cnt
FROM
    demo.users AS u
    LEFT JOIN demo.orders AS o
        ON o.user_id = u.id
WHERE
    u.active
GROUP BY
    u.id;
```

- 数组参数 `= ANY($1::bigint[])` 与 `unnest` 默认可用。
- 改写前确认基数：`JOIN` 可能放大行数，`= ANY` 不会；两者结果语义要先对齐。

### 4.3 覆盖策略：`DELETE`+`INSERT`、`TRUNCATE`、UPSERT（PERF-14）

- 默认 **PG 12+ 支持 `INSERT ... ON CONFLICT`（`[9.5+]`）**，可用于幂等 upsert，但仍需注意唯一约束覆盖与膨胀；仅当显式声明目标为 **GP 6.6 / PG 9.4** 时不可用。
- `DELETE` + `INSERT`：按分区或变更集合切片覆盖的合理选择；风险在删除范围与重建范围不一致（见 `AP-03`）。
- `TRUNCATE`：整表重载、可接受 `ACCESS EXCLUSIVE` 锁且无外键/并发读时使用；GP 上分区交换
  另有 `EXCHANGE PARTITION` 等方言。
- 在需要模拟 upsert 时（或面向 GP 6.6 / PG 9.4）：用“先查后插”会产生竞态；用捕获 `unique_violation` 模拟时，异常块是子事务，
  有额外代价，且并发下仍可能冲突。任何“等价 upsert”都必须说明竞态窗口与重试策略。
- `INSERT ... RETURNING` 可用，可用于取回生成值，减少二次查询。

### 4.4 临时表 staging（PERF-23）

临时表是结构选择，不是“把 SQL 拆短”的手段。四项声明清单（为什么必须物化、被引用几次、
生命周期、清理与失败路径）与“默认不加表”的四种情形**只在** `00-风格与边界.md` §3 定义，
本节不重复；本节只给性能判据。

- `CREATE TEMPORARY TABLE ... AS SELECT` 会全量物化，且新表通常没有统计信息；后续查询可能
  走糟糕的计划。必要时对临时表 `ANALYZE`。
- 临时表不自动继承源表的索引、约束与分布；GP 上临时表的分布策略会影响 motion。
- `ON COMMIT DROP` 与显式 `DROP` 的选择见 `AP-06` 与 `01-基线规范.md`；连接池事务模式下，
  会话级临时表可能跨请求残留。
- 临时表不是“免费缓存”：临时空间、WAL（临时表通常不写 WAL，但排序/哈希仍可能落盘）、
  与 GP segment 本地磁盘都要计入 `workload-required`。
- CTE 物化行为随引擎变化：PG 12+ 默认内联单次引用非递归 CTE 并支持 `[NOT] MATERIALIZED`（`PERF-20`），而显式 GP 6.6 / PG 9.4 目标下 CTE 恒物化。

### 4.5 WAL 与膨胀

`DELETE`+`INSERT`、批量 `UPDATE`、索引重建都会增加 WAL 与表/索引膨胀。计划形状不能回答这些；
需要 `pg_stat_statements` 的 `temp_blks_written`、`blk_read_time`/`blk_write_time`（需
`track_io_timing`）、WAL 生成速率、表大小前后对比与膨胀测量。GP 的 WAL 与 AO 表行为不同，
不能套用。

### 4.6 大删除/大更新的分块（PERF-40）

- 一次删除/更新上百万行会拉长事务、放大 WAL、留下大量死元组，并长期持锁。
- 按主键或时间片分块，每块独立事务；块大小由锁容忍度与回滚代价决定，需 C 档证据。
- 函数不能 `COMMIT`；默认 PG 12+ 可由过程（`[11+]`，受 `PLS-44` 约束）分块提交，或由外层调度分次调用；显式 GP 6.6 / PG 9.4 目标无过程，只能由调用方分次调用并在契约里写明“一次调用只处理一块”。
- 删除范围仍按 `AP-03` 与 `01-基线规范.md` 的业务范围核对，不能只看日期片。

### 4.7 日期/时间谓词（PERF-29、PERF-30）

写法规则（列侧裸露、右侧显式类型、半开区间、文本列、相对时间窗）**只在**
`00-风格与边界.md` §4 定义；`04-固定风格.md` §6 给默认写法。本节只回答“怎么判风险”。

- 对过滤列套 `::date`、函数或隐式 cast，会让普通 B-tree 索引与分区裁剪失效，通常只能走
  全表/全分区扫描——这是 `static-risk`，不是实测结论。
- 列已是 `date` 时，`col::date` 是冗余 cast；直接比较。
- 只有列类型确实不是日期、且无法改列或建立同表达式索引时，才允许列侧 cast；必须标
  `plan-required`，并说明为什么没有可索引的等价写法。
- 上述判断都是静态风险；是否真的走索引、是否分区裁剪，仍需 `EXPLAIN`。本技能不连库，
  不把“写法更规范”当成“计划已验证”。

## 5. 并发、锁与事务

### 5.1 事务长度（PERF-15）

- 函数体没有显式事务控制；`COMMIT`/`ROLLBACK` 只在过程（`CALL`，PG 12+ 默认可用）中合法。
- 锁在事务结束前不会释放；函数内做外部调用、等待用户输入、批量逐行处理都会拉长锁持有时间。
- `statement_timeout`、`lock_timeout` 与 `idle_in_transaction_session_timeout`（`[9.6+]`）在 PG 12+ 默认可用（显式 PG 9.4 / GP 6.6 无 `idle_in_transaction_session_timeout`）。
- 长事务还会阻止 `VACUUM` 回收，导致膨胀；这是 `workload-required` 的结论。

### 5.2 加锁顺序（PERF-16）

多行/多表写入保持一致的加锁顺序，能降低死锁概率。能用单条 `UPDATE` 完成时不要拆成多条；
若必须多步，先按固定顺序 `SELECT ... FOR UPDATE` 锁定目标行，再执行更新。

- `pg_stat_database.deadlocks` 可用于确认是否发生过死锁。
- `log_lock_waits`、`deadlock_timeout` 可用；开启前评估日志量。
- PG 12+ 默认可用 `pg_blocking_pids()`（`[9.6+]`）；仅显式 PG 9.4 / GP 6.6 目标需查 `pg_locks` 手工关联 `transactionid` 与 `pid`。

### 5.3 行锁范围（PERF-17）

- `SELECT ... FOR UPDATE` 只锁必要行；`NOWAIT` 可避免无限等待，但调用方必须处理失败。
- **默认 PG 12+ 可用 `SKIP LOCKED`**（`[9.5+]`）处理并发队列表；仅显式声明目标为 GP 6.6 / PG 9.4 时不可用（改用 `NOWAIT`）。
- 若目标为 GP，行锁与分布键相关：跨 segment 的更新可能产生更多 motion 与锁等待，`[GP-待验证]`。

### 5.4 advisory lock（PERF-16 补充）

- `pg_advisory_lock` / `pg_advisory_xact_lock` 默认可用；事务级锁在事务结束自动释放，
  会话级锁必须显式释放。
- 连接池复用会让会话级 advisory lock 跨请求残留；使用前确认池化模式与释放路径。
- advisory lock 的 key 空间要集中管理，避免不同业务用相同 key 互相阻塞。
- GP 上 advisory lock 是否跨 segment 一致，`[GP-待验证]`；不要假设与社区 PG 相同。

### 5.5 连接池与会话状态（PERF-18）

连接池（如 PgBouncer 的 transaction 模式）会在事务结束后把连接交给其他客户端。函数或调用方
不得依赖以下会话状态跨语句存活：

- 临时表（`ON COMMIT DROP` 可降低残留，但不要在事务外假设表还在）；
- 会话级 `SET`（用 `SET LOCAL` 限定在事务内）；
- 会话级 advisory lock；
- prepared statement（transaction 模式下服务端 prepared statement 行为随驱动与池化配置变化）；
- 序列 `currval`、游标、`LISTEN` 等。

这些属于 `workload-required`：需要池化配置、并发模型与故障注入验证，不能只看代码。

### 5.6 函数内不做 DDL（PERF-39）

- `ALTER TABLE`、`DROP INDEX`、`CREATE INDEX` 通常取强锁；函数在调用方事务内运行，锁会持有到
  事务结束，期间可能阻塞整表读写。
- `CREATE INDEX CONCURRENTLY` 不能在事务块/函数内执行；GP 6.6 则完全不支持 `CONCURRENTLY`。
- 把 DDL 移到部署脚本或维护窗口；函数只做 DML。分区维护类函数必须写明锁范围、执行窗口与失败回滚。
- 需要在线建索引时，由库负责人在维护窗口执行，并评估磁盘空间与复制延迟；这是 C 档事项。

## 6. 查询形状

### 6.1 CTE 物化（PERF-20）

- **默认基线 PG 12+ 对单次引用且非递归/无副作用的 CTE 默认内联**，并支持显式 `MATERIALIZED` / `NOT MATERIALIZED`；仅当显式声明目标为 GP 6.6 / PG 9.4 时 CTE 恒物化且不支持该修饰符。
- “把子查询拆成 CTE”或加注 `[NOT] MATERIALIZED` 都可能改变计划，是结构变更，不是排版。
- GP 7 基于 PG 12 且受 ORCA 影响，GP 6.6 的结论不能反推到 GP 7，反之亦然。

### 6.2 子查询与 JOIN（PERF-21、PERF-31）

- `IN (SELECT ...)`、`EXISTS`、`JOIN` 的语义与重复行行为不同；改写前先验证行数与重复行。
- `NOT IN` 遇到 NULL 会产生空结果；改写成 `NOT EXISTS` 前必须确认 NULL 语义。反连接的计划
  选择（Hash Anti Join / Nested Loop Anti Join）由 B 档回答。
- 半连接/反连接的规划能力随版本变化；PG 12 的计划不能直接代表 PG 15+ 或 GP，反之亦然。

### 6.3 分页（PERF-13）

- 深 `OFFSET` 会扫描并丢弃前面的行；页深越大代价越高。
- keyset 分页用“上一页最后一行”的排序键作为起点；排序键必须唯一或加上唯一列打破并列，
  否则会漏行/重复行。
- 行比较 `(created_at, id) > (...)` 默认可用；`NULLS FIRST/LAST` 必须与索引和查询一致。
- 游标/`FETCH` 也能分页，但长事务持有快照与锁，需 `workload-required` 评估。

### 6.4 宽扫描与结果集（PERF-22、PERF-44）

- `SELECT *` 在函数落表或对外结果中会放大 IO、网络与列依赖；显式列是稳定性要求。
- `UNION` 去重有排序/哈希代价；语义允许时用 `UNION ALL`，但这是语义变更，需批准（`PERF-32`）。
- 集合返回函数（`RETURNS TABLE`/`SETOF`）在调用方 `LIMIT` 时不一定能下推；是否流式取决于
  函数写法与版本，`plan-required`。
- SRF 放在 `SELECT` 列表会按行展开（PG 10+ 改为最小公倍数行为变为逐行同步/错误），优先用 `FROM` / `LATERAL`，改写前后核对行数与 NULL 行为（`PERF-44`）。

### 6.5 函数调用与内联（PERF-24）

- SQL 语言函数在满足条件时可能被内联；PL/pgSQL 函数不会被内联。内联条件随版本变化，
  不能跨版本外推内联行为。
- `STABLE`/`IMMUTABLE` 是优化器提示，不是“加速开关”；误标会破坏正确性（见 `B-04`）。
- `COST`、`ROWS` 影响规划，但没有实测依据时不要随意设置；`PARALLEL`（`[9.6+]`）在 PG 12+ 默认可用（GP 6.6 / PG 9.4 不可用）。

### 6.6 触发器（PERF-25）

- 行级 `BEFORE/AFTER` 触发器每行执行一次；大批量写入时开销按行放大。
- `WHEN` 条件可以避免不必要的函数调用，但条件本身也要逐行求值；表达式复杂度要控制。
- 语句级触发器 + 转换表（transition tables，`[10+]`）在 PG 12+ 默认可用（显式 GP 6.6 / PG 9.4 目标不可用）。
- 触发器中做查询/写入会放大锁与 IO；能移到调用方的批量逻辑不要放进行级触发器。

### 6.7 集合运算与去重（PERF-32、PERF-33）

- `UNION` 隐含去重，通常需要排序或哈希；`UNION ALL` 不去重。选择依据是语义，不是“哪个快”。
- `DISTINCT ON (k)` 取每组首行时，`ORDER BY` 必须以 `k` 开头，才可能利用索引顺序；否则仍排序。
- 整行 `DISTINCT` 往往是连接放大或建模问题的信号；先查基数，不要只靠去重收尾。
- 去重会改变重复行语义；对落表函数来说，这是行为变更，必须做新旧结果对比。

### 6.8 排序、窗口与索引顺序（PERF-34）

- `ORDER BY` 的列序、方向与 `NULLS` 顺序若与索引一致，可省去排序；否则需要 `Sort`，大结果集
  可能溢写磁盘。
- 窗口函数的 `PARTITION BY`/`ORDER BY` 通常需要排序；分组基数大时，窗口函数不一定优于自连接。
- 比较两种写法时看 `Sort` 的行数、`Sort Method`（内存/磁盘）与 `WindowAgg` 的输入行数，而不是
  只看总 cost。

### 6.9 通配、列表与参数（PERF-35、PERF-36）

- `LIKE '%x%'`、`~ 'x'`（非锚定）无法用 B-tree 定位；可选 `pg_trgm` + GIN、全文检索或前缀匹配。
  前缀匹配可用 B-tree，但受 collation 影响，非 C collation 下仍可能无法用普通索引。
- 上千个值的 `IN (...)` 会增加解析与计划时间；优先 `= ANY($1::type[])`、`unnest` 或临时表 join。
- 动态 SQL 中值必须 `USING` 绑定，标识符必须 `%I`；绑定解决注入，不解决计划问题（`PERF-19`）。
- GP 上大列表还可能影响分布判断与 motion 选择，需 B 档确认。

### 6.10 估算偏差与扩展统计（PERF-41）

- 估算 1 行、实际百万行，通常说明统计过期、表达式不可估算、跨列相关或数据倾斜。
- 先 `ANALYZE`、提高相关列的 `default_statistics_target`，或改写为可估算的谓词。
- 多列相关性在默认 **PG 12+ 可用 `CREATE STATISTICS`（`[10+]`）**（MCV 统计在 PG 12+ 新增）；仅显式 GP 6.6 / PG 9.4 目标不可用，只能靠改写、拆分查询或物化中间结果并用 B 档验证。
- 不要用 `OFFSET 0`、`MATERIALIZED` 之类偏方掩盖估算问题。

### 6.11 循环与异常块的函数开销（PERF-42、PERF-43）

- `EXECUTE` 放在循环里会每次解析与计划；能提到循环外就提，能集合化就集合化。
- `v_sql := v_sql || ...` 在长循环里反复复制；优先 `string_agg`/`array_agg` 在 SQL 里聚合。
  `array_append` 也不是零成本，不要假设 O(1)。
- 带 `EXCEPTION` 的块进入时建立子事务；用它做“先试再回退”的常规分支会放大开销，并可能与
  长事务、vacuum 交互。能用显式谓词判断的，不要用异常捕获做分支。
- 必须捕获时只包最小语句，捕获具体 `SQLSTATE`，保留 `SQLSTATE`/`MESSAGE_TEXT` 并重抛（`AP-02`）。

## 7. Greenplum 6.6 专属（按需启用）

本节仅在调用方或用户显式声明目标引擎为 Greenplum 6.6 时适用；默认原生 PostgreSQL 12+ 任务跳过本节。

### 7.1 分布与 motion（PERF-26）

- 分布键决定数据落在哪个 segment；连接键与分布键不一致会产生 redistribute/broadcast motion。
- 分布键选择要看主要连接与聚合模式，不能只看单条查询；倾斜会让单个 segment 成为瓶颈。
- `gp_segment_id` 可用于检查分布；gp_toolkit 的倾斜视图（如 `gp_skew_coefficients`）可用性
  `[GP-待验证]`。
- 社区 PG 的“加索引就快”在 GP 上不成立：大表扫描常由分区裁剪、列存与 motion 决定。

### 7.2 分区与统计

- GP 6.6 使用自己的分区语法（`PARTITION BY ...`、`SUBPARTITION BY ...`、
  `ALTER TABLE ... EXCHANGE PARTITION`、`SPLIT DEFAULT PARTITION`），与 PG 10+ 的声明式分区
  不是一回事；不要把两边 DDL 互译。
- 分区裁剪依赖谓词形态与统计；对分区表 `ANALYZE` 的传播规则 `[GP-待验证]`。
- 对分区键包函数、隐式 cast 或使用无法在计划期推断的参数，可能退化为扫描全部分区；需 B 档确认。
- 动态 SQL 拼接分区名时，注意标识符引用与分区存在性校验（见 `AP-01`、`PERF-19`）。

### 7.3 AO 表

- `WITH (appendonly=true, orientation=column)` 等存储参数影响压缩、更新与空间回收；
  行存/列存的选择属于建模决策，不是索引能替代的。
- AO 表的 `UPDATE`/`DELETE` 行为与堆表不同，膨胀与 `VACUUM` 语义 `[GP-待验证]`。
- 不要把 PG 的 HOT update、fillfactor、visibility map 经验直接套到 AO 表（`PERF-45`）。

### 7.4 `EXPLAIN` 解读

- GP 的 `EXPLAIN` 输出是 slice/segment 视角，含 `Motion`、`Broadcast`、`Redistribute`；
  不能按社区 PG 的 `Seq Scan`/`Index Scan` 单节点模型解读。
- GP 6.x 的 `EXPLAIN` 文档列出 `ANALYZE`、`VERBOSE`、`COSTS`、`BUFFERS`、`TIMING`、
  `FORMAT TEXT|XML|JSON|YAML`；实际输出以目标集群为准。
- `EXPLAIN ANALYZE` 会真实执行，代价可能很高；在生产上先用 `EXPLAIN`（不执行），
  需要实际行数时在隔离环境或只读副本上做。

### 7.5 不可移植结论

- 索引可用性、分区裁剪、`ANALYZE` 采样、CTE 物化、并行查询、`ON CONFLICT`、`SKIP LOCKED`、
  RLS 都不能按社区 PG 版本推断 GP。
- 反向同样成立：GP 的分布与 motion 经验不能带进 PostgreSQL 建议。

### 7.6 ORCA 与资源队列（PERF-46）

- GP 6 默认使用 ORCA（Pivotal Optimizer）；`SET optimizer = off` 会切换到规划器，计划可能显著不同。
  计划文本中的 `Optimizer: Pivotal Optimizer` 可作为判断依据。
- 比较两种写法时固定优化器设置；不要一边开 ORCA 一边关。
- GP 的并发与内存受资源队列/资源组限制；压测必须使用与生产相同或可比的队列配置，
  否则吞吐与排队时间不可迁移。
- 不要用 PostgreSQL 的 cost 数值直接比较 GP 计划。

## 8. 测量方法与证据采集

### 8.1 用户侧 `EXPLAIN` 模板（PG 12+ 默认可用）

以下命令由用户在目标库执行；本技能不连接数据库、不代跑，也不把结果升级为自身实测结论。

```sql
EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)
SELECT
    ...
FROM
    ...
WHERE
    ...;
```

- `ANALYZE` 会执行语句；写语句请放在事务里并 `ROLLBACK`，同时计入序列与外部副作用。
- `BUFFERS` 显示共享块命中/读取；`track_io_timing` 开启后才有块读写时间。
- `TIMING` 默认开启，逐节点计时有开销；只关心计划形状时可 `TIMING OFF`。
- PG 12+ 支持 `EXPLAIN (SETTINGS)`；`EXPLAIN (WAL)` 需 `[13+]`（PG 12 / GP 6.6 / 9.4 不可用）。
- 观察点：估算 vs 实际行数、`loops`、`Rows Removed by Filter`、`Heap Fetches`、
  `Sort Method`、临时文件与 buffers；不要只看总 cost。

### 8.2 语句统计（PERF-27）

- `pg_stat_statements` 需要 `shared_preload_libraries` 与重启；GP 6.6 的安装与列名 `[GP-待验证]`。
- PG 12 及以下的列是 `total_time`、`mean_time`、`rows`、`shared_blks_hit`、`shared_blks_read`、
  `temp_blks_written`、`blk_read_time`、`blk_write_time` 等；13+ 改名为
  `total_exec_time`/`mean_exec_time`。查询前先核对目标库 PG 版本，避免列不存在。
- 归一化查询文本会隐藏参数；要定位具体参数，结合 `auto_explain` 或应用日志，注意脱敏。
- 口径：按总耗时、调用次数、平均耗时、行数分别排序；只看平均值会漏掉慢尾与高频小查询。

### 8.3 锁与等待

- PG 12+ 默认可用 `pg_stat_activity.wait_event_type`/`wait_event`（`[9.6+]`）与 `pg_blocking_pids()`；仅显式 PG 9.4 / GP 6.6 目标没有上述列/函数，只能看 `waiting` 与手工关联 `pg_locks`。
- `pg_locks.waitstart` 为 `[14+]`，在 PG 12 与 PG 13 目标不可用。
- 死锁计数看 `pg_stat_database.deadlocks`；锁等待日志看 `log_lock_waits`。

### 8.4 计划不能回答的问题

以下必须 `workload-required`：吞吐、QPS、并发下的锁竞争、WAL 生成量、表/索引膨胀、
临时空间、尾延迟、连接池排队、GP 的 segment 倾斜与磁盘 IO。

### 8.5 记录模板

```text
证据档位：static-risk / plan-required / workload-required / not verified
引擎与版本：PostgreSQL 12+（写明具体版本号；如 12.x / 14.x / 16.x 或可选 GP 6.6）
数据快照：表行数、统计信息时间、是否 ANALYZE、参数值
执行方式：只读副本 / 事务回滚 / 隔离环境
观测结果：计划节点、估算 vs 实际行数、buffers、耗时
不能回答：吞吐、并发、WAL、膨胀、尾延迟（逐项写明）
结论：只写该快照下的事实；不外推
```

## 9. 参考来源中不可直接移植的结论

以下列出参考来源中不可直接套用的假定：**PG 13+ / 平台专有特性**在默认 PG 12+ 下不能直接假定；**PG 9.5–12 特性**在 PG 12+ 默认可用，仅在显式 GP 6.6 / PG 9.4 目标时降级。

| 来源写法 | 问题或版本前提 | 本技能处理 |
|---|---|---|
| `CREATE INDEX ... INCLUDE (...)` | `[11+]` | PG 12+ 可用；显式 GP / 9.4 用多列索引 |
| BRIN 索引 | `[9.5+]` | PG 12+ 可用；显式 GP / 9.4 不写 |
| `INSERT ... ON CONFLICT` | `[9.5+]` | PG 12+ 可用；显式 GP / 9.4 改用 `DELETE`+`INSERT` 或捕获冲突 |
| `SKIP LOCKED` | `[9.5+]` | PG 12+ 可用；显式 GP / 9.4 用 `NOWAIT` |
| `CREATE INDEX CONCURRENTLY` | 原生 PG 可用；GP 6.6 文档不支持 | PG 中也不得放进函数；维护窗口执行 |
| RLS 策略性能 | `[9.5+]`；GP `[GP-待验证]` | PG 12+ 按需评估；显式 GP / 9.4 不适用 |
| `auth.uid()`、`auth.role()` | Supabase 平台函数 | 本技能无此函数；用调用方身份参数或 `current_user` |
| `total_exec_time`/`mean_exec_time` | `[13+]` 列名 | PG 12 用 `total_time`/`mean_time`；13+ 用新列名 |
| `EXPLAIN (WAL)`、`pg_locks.waitstart`、`MERGE` | `[13+]` / `[14+]` / `[15+]` | 需先确认目标 PG 主版本达到对应门槛 |
| `pg_stat_progress_vacuum`、`wait_event`、`pg_blocking_pids()` | `[9.6+]` | PG 12+ 默认可用；显式 GP / 9.4 不可用 |
| `PARALLEL SAFE` | `[9.6+]` | PG 12+ 按并发安全性标注；显式 GP / 9.4 不写 |
| `CREATE PROCEDURE`/`CALL`/`COMMIT` | `[11+]` | PG 12+ 可用（受 `PLS-44` 约束）；显式 GP / 9.4 用函数 |
| `CREATE STATISTICS` | `[10+]` | PG 12+ 可用；显式 GP / 9.4 不可用 |
| `GENERATED ... STORED` | `[12+]` | PG 12+ 可用；显式 GP / 9.4 不可用 |
| `REINDEX CONCURRENTLY` | `[12+]` | PG 12+ 可用；显式 GP / 9.4 用普通 `REINDEX` |
| `CREATE DOMAIN` 全覆盖、`fn_`/`pr_` 命名前缀 | 命名与类型体系决策，不是性能规则 | 由项目风格说明与 `09` 层处理，本层不采纳 |
| “快 100–1000 倍”“小 5–20 倍” | 来源主张，非本技能实测 | 只作背景，不写进结论 |
| 临时表 CTAS 无统计 | 来源未强调 | 本技能要求 `ANALYZE` 或说明为何不需要 |
| `EXPLAIN (ANALYZE)` 在生产直接跑 | 会真实执行 | 由用户在隔离环境/只读副本执行，本技能不代跑 |

## 10. 性能结论写作模板（PERF-28）

决策顺序：

1. 能否只凭代码/DDL 判断？能 → `static-risk`，写“需验证”，不写快慢。
2. 需要计划才能判断扫描/连接/排序/motion？→ `plan-required`，列出待跑语句与预期观察点。
3. 涉及吞吐、并发、锁、WAL、膨胀、尾延迟？→ `workload-required`，列出采集指标与负载模型。
4. 用户已在代表性快照上执行过计划？→ 仍标 `plan-required`，把用户提供的计划作为外部上下文引用；
   本技能不执行计划，也不把自己的静态检查当成计划证据。
5. 什么都没做？→ `not verified`，明确写出来。

句式：

```text
[PERF-02][plan-required] 复合索引列序可能无法支撑仅按 created_at 的过滤；
需由用户在 <表> 上用代表性参数执行 EXPLAIN，确认是否走索引及估算行数。
当前不能得出“更快/更慢”的结论。
```

禁止句式：

- “加了索引，性能提升 10 倍。”（无证据、无快照）
- “改成 JOIN 一定比子查询快。”（计划相关，需验证）
- “GP 上这样写肯定比 PG 快。”（跨引擎不可比）
- “静态检查通过，所以性能没问题。”（静态检查只到 A 档）

## 11. ETL 路径去重与稀疏增量（PERF-47…PERF-54）

### 11.1 先画路径，再改 SQL（PERF-51）

ETL 函数的第一份产出不是优化后的 SQL，而是读取与物化路径表，至少包含：

| 函数/分支 | 执行模式 | 源表与窗口 | 业务键/粒度 | 过滤/关联/聚合 | 物化点与引用次数 | 目标写入 |
|---|---|---|---|---|---|---|
| `<function>/<branch>` | `sparse_incremental` / `explicit_range` / `full` | `<table>`, `<window>` | `<key>`, `<grain>` | `<operation>` | `<temp/CTE>`, `<count>` | `<target>` |

只依据 SQL 文本标记 `observed`；缺少 DDL、版本、分布键、行数或调用参数时写 `unverified`。路径表用于证明“哪一次扫描被复用/删除”，不能把计划或速度推断成已验证。

### 11.2 稀疏集合与删除重建同源（PERF-47）

当 `update_time` 或变更标记命中多个不连续业务日期/月时，先物化或构造去重的实际集合：

```sql
WITH changed_period AS (
    SELECT DISTINCT
        a.target_date
    FROM
        demo.src_daily AS a
    WHERE
        a.update_time >= p_lookback
        AND a.update_time < p_batch_ts
)
DELETE FROM demo.dwd_daily AS t
WHERE EXISTS (
    SELECT 1
    FROM changed_period AS c
    WHERE c.target_date = t.target_date
);
```

插入路径必须对同一 `changed_period` 使用相同过滤与粒度；不能把它降级为 `min(target_date)` 到 `max(target_date)` 的连续区间。显式区间重算继续使用参数区间，逻辑删除继续按原有标记语义处理。若删除与插入跨语句，集合可物化；若只在一条语句内使用，优先 CTE/子查询。该形状只能静态说明避免了空洞日期的候选重建，实际计划仍为 `plan-required`。

### 11.3 同源窗口与低粒度公共结果（PERF-48）

对相同源表、相同窗口、相同业务键的过滤、关联和聚合，先建立一份公共结果，再按需要展开到明细、时间点或曲线粒度。不得在“主源分支”“备用源分支”“告警分支”“写入分支”各自重复同一窗口扫描。保留告警、冲突和校验分支，但让它们读取公共结果或同一变更集合。改写前后必须核对行数基数，避免把一对多关联提前合并造成重复。

### 11.4 主源有效值短路备用源（PERF-49）

“有值”必须按业务定义判断；对数值列，真实 `0` 是有效值，不等同于 `NULL` 或无行。推荐先聚合主源，再只对主源没有有效值的业务键聚合备用源：

```sql
WITH primary_value AS (
    SELECT
        p.business_key
        , max(p.value) AS value
    FROM
        demo.primary_src AS p
    GROUP BY
        p.business_key
)
, fallback_value AS (
    SELECT
        f.business_key
        , max(f.value) AS value
    FROM
        demo.fallback_src AS f
    WHERE NOT EXISTS (
        SELECT 1
        FROM primary_value AS p
        WHERE p.business_key = f.business_key
            AND p.value IS NOT NULL
    )
    GROUP BY
        f.business_key
)
SELECT ...;
```

保留原有去重、冲突优先级和“仅备用源存在”的输出；若主源存在多行但聚合结果为 `NULL`，不能误判为有效。只凭文本可判定短路条件是否存在，备用扫描的实际计划标为 `plan-required`。

### 11.5 单次物化与保留条件（PERF-50）

临时表/中间表逐张说明：来源、粒度、引用次数、物化原因、生命周期、清理和失败路径。只转存一次且没有写入隔离、跨语句复用、独立 `ANALYZE` 或无法表达的边界时，合并到 CTE/子查询；不要为了“结构清晰”保留一张同粒度复制表。跨语句复用或需要先冻结结果再 `DELETE`/`INSERT` 时可以保留，并把该理由列入路径表。减少物化是结构改变，行为等价需用离线样例核对，计划标签仍为 `plan-required`。

### 11.6 离线边界样例

至少准备以下输入/期望关系，不连接数据库、不执行 SQL：

| 场景 | 必查不变量 |
|---|---|
| 变更日期 `D1,D3` | 删除集合与重建集合均为 `{D1,D3}`，不包含 `D2` |
| 显式区间 `D1..D3` | 仍覆盖连续区间，不被稀疏集合规则替换 |
| 逻辑删除 `D1` | 保持原同步删除/标记语义，且不恢复已删除行 |
| 主源值 `0`、备用源值 `9` | 结果为主源 `0`，备用源不聚合该键 |
| 仅备用源键 | 结果保留备用源键 |
| 主备冲突/重复行 | 维持原去重与冲突优先级 |
| 无变更集合 | 不执行覆盖写入；空集合不使用哨兵日期 |
